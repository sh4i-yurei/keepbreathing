Notes from the Build▋

What I'm learning as I go, written down while it's fresh. Filter by tag.

I've been putting this together over the last couple of days, mostly in downtime between shifts at work, and last night I stayed up until about 2 AM getting it across the line. Classes start Monday, and I want the site mostly finished (short of the project blog posts) before the semester eats my evenings. Before I got started I read a handful of tutorials and watched some Learn Linux TV videos, because self-hosted mail has a well-earned reputation for being fussy and I wanted the shape of the thing before I typed the first command.

The contact form on keepbreath.ing has been sitting there as static HTML since I built the site for my capstone last term. Wiring up the backend is finally on the list. Before I did that, I needed the piece under the form: a working contact@keepbreath.ing address that I can both send from and receive on, with my Gmail as the actual inbox behind it.

Any reply I send from Gmail would otherwise leak the address I'm replying from, and I don't want a public contact page that ends up publishing my personal Gmail every time I answer someone. I knew this going in when I planned the site. It just took getting to this phase of the project to actually build the fix.

Free-tier services do the whole two-way-address thing for you. I self-hosted it instead. It's cheaper long-term, I get to set it up the way I want, and I keep control over my data. I also just wanted to know how the machine works. Security has been a priority for me from the beginning of this site, so building the mail path myself, where I could see what was happening at each step, felt like the right call.

This post is about the mail identity. The next one, once I've wired the endpoint in, is about the form.

The address and the mail server

The public-facing address is contact@keepbreath.ing. The mail server behind it lives at mail.keepbreath.ing, on its own A record with its own reverse DNS. Keeping the mail infrastructure on a subdomain keeps its reputation scoped to that subdomain instead of spilling onto the apex.

The address itself is really a set of DNS records. As long as those records stay valid, whatever server is answering underneath is replaceable. I renamed the droplet halfway through this build (more on that in Step 3), and the address kept working straight through the change because the address was in DNS and not on the box.

Step 1: receiving with Cloudflare Email Routing

I set up the inbound side using Cloudflare Email Routing, which is free and doesn't need a server of its own. I added a rule that forwards contact@keepbreath.ing into my Gmail. That put a working inbox behind the public address, and it meant anyone writing to contact@ would never see the Gmail address underneath.

I did the receiving side first because Step 4 was going to send a verification link to contact@, and I needed a working inbox to click through when it arrived.

I tested the setup by sending a message from the droplet, which had no email authentication configured yet. Cloudflare refused it:

550 5.7.26 Cannot forward emails that are not authenticated

A separate spoofed-sender test came back with a similar refusal. Cloudflare will not forward mail from a sender it can't authenticate. To test the forwarding rule properly I needed to send from an authenticated sender, so I sent a message from my personal Gmail account, and that one went through immediately.

Cloudflare is doing exactly what most mail receivers on the internet do with unauthenticated mail. Step 3 is where I built the authentication so my own sending would pass those same checks.

Step 2: sending my own mail with Postfix

Free Gmail can't send from a custom domain through Google's own servers, because that's a paid Workspace feature. What free Gmail can do is log into an outside SMTP server, hand off a message, and let that server handle delivery to the recipient. So to reply as contact@, I needed my own SMTP server for Gmail to log into.

I chose Postfix. It's well-documented and most tutorials use it, which made it a sensible default for what I was doing. For the Postfix + Dovecot structure I leaned heavily on Christoph Haas's ISPmail guide, which is the most thorough self-hosted mail tutorial I found and the one many other guides cite as their starting point. Most of this configuration happened at the terminal rather than in a UI. I still struggle with wrapping my head around a lot of Linux commands, but I get overwhelmed hunting through nested UIs faster than I do sitting with a config file, so the more I do at the terminal the more comfortable I get.

Postfix on this box does two related jobs. It runs a submission service on port 587 that Gmail authenticates to and hands outgoing mail to, and it runs a relay on port 25 that delivers those messages onward to the recipient's mail server. It's the same daemon running as two services.

I built the whole thing up in layers, starting with identity, then TLS, then authentication, then the submission port itself, and finally opening the firewall. Between most of these steps I got up, walked around, and came back to it. My ADHD means I work in short focused bursts with breaks in between, and a config file this dense is exactly the kind of thing that starts to blur if I stare at it too long.

Postfix identity

There were three settings I had to change from the installer defaults.

The first was myhostname = mail.keepbreath.ing, which is what Postfix announces when it greets another server. It has to match the mail DNS record, the certificate's Common Name, and the reverse DNS. The Debian installer had set it to the bare keepbreath.ing, which would have failed every one of those matches, so I corrected it.

The second was mydestination = $myhostname, localhost, which is the list of domains this server considers local. I deliberately kept the parent domain off the list. Cloudflare is the MX for keepbreath.ing, so if this box also claimed the domain it would try to keep mail for @keepbreath.ing locally, and that would break the inbound routing from Step 1. The installer default included both the parent domain and a localhost.ing artifact from the .ing TLD, both of which I removed. The .ing artifact caught me by surprise the first time I read the config. Most defaults assume a .com domain, and there are a few places in the mail stack where a short TLD makes the automatic naming behave oddly.

The third was mynetworks = 127.0.0.0/8 [::1]/128, which sets loopback as the only network trusted to relay without authenticating. Only processes running on the box itself get that trust. Gmail isn't on the box, so Gmail has to log in like any other remote client. That's half of the defense against becoming an open relay for the internet.

TLS

No password is going over the wire in cleartext, so TLS has to work before I can turn on authentication.

I pointed Postfix at a Let's Encrypt certificate for mail.keepbreath.ing, obtained via DNS-01 through Cloudflare because I didn't want to expose an HTTP challenge endpoint on the box. The certificate's Common Name is mail.keepbreath.ing, which matches myhostname. A Cloudflare Origin Certificate wouldn't work in this position because only Cloudflare trusts those, and a self-signed certificate would be refused by mail clients.

For port 25 I set smtpd_tls_security_level = may, which is opportunistic encryption. It uses TLS if the sender's server supports it and accepts plaintext otherwise. That's the right posture on port 25, because you can't force every mail server on the internet to have TLS. Port 587 requires TLS, and that setting comes a few paragraphs down.

Somewhere around the end of the TLS work I hit a wall and needed a real break. I stepped away from the terminal, grilled myself some bratwurst and rice pilaf, and let my brain digest what I'd wired up before coming back to authentication.

SASL through Dovecot

Postfix doesn't check submission passwords itself. It hands the check to a SASL provider. I used Dovecot as that provider, with no mailboxes and no IMAP running. The inbox lives in Gmail via the Cloudflare routing from Step 1.

The submission credential for contact@keepbreath.ing sits in /etc/dovecot/passwd as a SHA512-CRYPT hash. The plaintext is only in my offline password manager, because I need it once more in Step 4. Reading the file on the server exposes nothing usable to an attacker.

I disabled Dovecot's default PAM passdb explicitly, because a mail submission credential shouldn't double as a way to log into a Linux account.

Postfix and Dovecot talk to each other over a Unix socket that Dovecot places inside Postfix's chroot at /var/spool/postfix/private/auth. Two Postfix directives point at that socket:

smtpd_sasl_type = dovecot
smtpd_sasl_path = private/auth

I confirmed the credential worked before exposing anything to the network:

$ doveadm auth test contact@keepbreath.ing
auth succeeded

Seeing that auth succeeded line was the first real sign the plumbing was actually connected. Everything before it had been configuration on faith.

The submission service on port 587

Port 25 accepts inbound mail from other servers. Port 587 is a separate service for authenticated outbound clients. Postfix runs both from the same daemon using per-port overrides in master.cf.

The 587 block overrides five settings from the defaults. It requires TLS, enables SMTP AUTH, adds the two open-relay guards, and gives the service its own log label so I can grep for it:

submission inet n       -       y       -       -       smtpd
  -o syslog_name=postfix/submission
  -o smtpd_tls_security_level=encrypt
  -o smtpd_sasl_auth_enable=yes
  -o smtpd_relay_restrictions=permit_sasl_authenticated,reject
  -o smtpd_client_restrictions=permit_sasl_authenticated,reject

The permit_sasl_authenticated, reject value on both restriction lines is what actually keeps the service from being an open relay. Any client that has authenticated is allowed to relay through the service, and anything else is refused. There's deliberately no permit_mynetworks on this service, because port 587 is meant for remote authenticated clients rather than local processes, and letting a local process relay through it would open a hole.

Before opening the firewall I ran an open-relay test with swaks. I connected to Postfix on the loopback, skipped authentication, and asked it to relay to an outside address. It refused:

554 5.7.1 <localhost[127.0.0.1]>: Client host rejected: Access denied

That refusal was the one I actually wanted to see. It's the whole point of the restriction lines above, and it landed exactly the way the config said it should.

The same test showed two other things I wanted to check. AUTH was only advertised in the EHLO reply after STARTTLS (the pre-STARTTLS EHLO didn't include AUTH at all), so a password can never be offered before the connection is encrypted. And the certificate presented was the real Let's Encrypt one, served over TLS 1.3.

Opening 587 in the firewall

Once the open-relay test passed, I added one inbound rule to the DigitalOcean Cloud Firewall for tcp/587 from 0.0.0.0/0 and ::/0. I added it via the DigitalOcean API using curl from my laptop. My DO API token lives in the laptop's password manager and has never been on the droplet. That token can create and destroy anything in the account, so there's no reason for it to sit on a server.

I considered restricting 587 to Google's IP ranges instead of leaving it open. Gmail's send-as relay uses a broad and shifting set of Google addresses, and keeping an allowlist current would be a maintenance chore. So I left the port open to everyone, and the port's protection is TLS, SASL authentication, and the open-relay guards. The consequence of leaving it open is that internet bots will try to brute-force the login. They won't guess a long random password, and if they somehow did, they still couldn't relay. Adding fail2ban to auto-ban repeated attempts is on my follow-up list.

I verified the port was reachable from an outside machine:

$ nc mail.keepbreath.ing 587
220 mail.keepbreath.ing ESMTP Postfix

Step 3: publishing SPF, DKIM, and DMARC

The next thing I set up was the DNS records that mail receivers use to decide whether to trust mail from my domain. If those records aren't right, no amount of well-configured Postfix helps. There are three of them, plus a reverse DNS record on the droplet's IP.

SPF

SPF is a DNS TXT record that names which servers are authorized to send mail for your domain. Cloudflare Email Routing had already published one for me:

v=spf1 include:_spf.mx.cloudflare.net ~all

That authorized Cloudflare's servers and nothing else. My droplet, now also a sender, wasn't on the list. A receiver checking SPF on mail from my IP would see the IP wasn't authorized to send as keepbreath.ing.

A domain has exactly one SPF record. Adding a second one breaks SPF entirely for the domain, so instead of publishing a new record I edited the existing one through Cloudflare's API:

v=spf1 ip4:YOUR.DROPLET.IP include:_spf.mx.cloudflare.net ~all

I kept ~all (softfail) rather than moving to -all (hardfail) for now. Softfail tells receivers to treat unauthorized senders as suspicious, and hardfail tells them to reject outright. I want to watch my own mail behave cleanly for a while before asking receivers to hardfail on anything.

DKIM

SPF checks the sending IP. DKIM goes further. It attaches a cryptographic signature to every outgoing message using a private key on the sending server, and it publishes the matching public key in DNS. Receivers use the public key to verify that a message really came from the domain and hasn't been altered in transit. Unlike SPF, DKIM signatures also survive forwarding.

I installed OpenDKIM as the signing daemon, generated a 2048-bit RSA key pair, and published the public key at mail._domainkey.keepbreath.ing. For the OpenDKIM configuration and its integration with Postfix I mostly worked from LinuxBabe's mail server tutorials, which walk through the signing setup and the follow-on OpenDMARC piece step by step. My selector is mail. Cloudflare's existing DKIM record uses a different selector (cf2024-1), so both records live in DNS without conflicting.

Two OpenDKIM defaults were wrong on this system, and I caught them from reading through the config carefully before touching anything else. The default socket is a Unix socket at /run/opendkim/opendkim.sock, which chrooted Postfix cannot reach. I changed it to inet:8891@localhost so Postfix could talk to it regardless of chroot, and this was the same problem I'd already run into with Dovecot. The second one is that /etc/default/opendkim is a legacy file that systemd ignores on modern distributions, which means all settings have to be in /etc/opendkim.conf instead. Catching both of these before starting the service saved me the debugging time I would otherwise have spent on them.

Then I wired OpenDKIM into Postfix as a milter, which is Postfix's plugin interface for filters that inspect or modify mail as it passes through:

smtpd_milters = inet:localhost:8891
non_smtpd_milters = inet:localhost:8891
milter_default_action = accept

The milter_default_action = accept line is deliberate. If OpenDKIM ever falls over, Postfix will pass mail through unsigned rather than dropping it. For a personal contact address I'd rather have quiet degradation than an outage.

I verified the DNS record against the private key with opendkim-testkey, which returned key OK. There's also a key not secure message that comes alongside, which is just the tool telling me I haven't set up DNSSEC on the domain, and DNSSEC isn't in scope for this build.

DMARC

DMARC sits on top of SPF and DKIM. It does two things at once. It tells receivers what to do with mail from your domain that fails both checks, and it asks receivers to send back reports about who is sending mail as your domain.

I published a minimal DMARC record at _dmarc.keepbreath.ing:

v=DMARC1; p=none; rua=mailto:contact@keepbreath.ing

p=none is monitor mode. It doesn't ask receivers to do anything to failing mail; it just asks them to send reports. I want to see the reports and confirm my own mail is passing both checks before tightening the policy to quarantine or reject. The reports come back to contact@, which the inbound routing from Step 1 forwards into Gmail.

The reverse DNS problem

I ran a test message through mail-tester, which grades outgoing mail against the standard authentication checks. It came back at 8.9 out of 10. The only real ding was RDNS_NONE.

Reverse DNS is a lookup that takes an IP address and returns a hostname. A receiver getting mail from my droplet's IP can ask DNS "what's the name of that IP?" and expect a well-configured mail server to answer with a name that matches its myhostname and forward-resolves back to the IP. A mail server whose reverse lookup goes nowhere, or points to a name that doesn't forward-resolve back, doesn't look trustworthy from the receiver's side.

Meanwhile in Gmail's Show Original view for the same message, SPF, DKIM, and DMARC all showed PASS, and the message had still gone to my Gmail spam folder. The rig gave me a near-perfect score and Gmail put the message in spam anyway. I couldn't find that gap explained in any of the tutorials I read, and I spent a while wracking my brain trying to find a path through it. Most of the useful information I ended up finding came from DigitalOcean's own DNS documentation and from digging through community forum threads where other people had hit the same issue.

The reason for the RDNS_NONE ding is a DigitalOcean-specific quirk in how droplet naming maps to PTR records. On DigitalOcean there's no separate PTR field for a droplet. The PTR record for a droplet's IP is derived from the droplet's name, and that name has to be a fully-qualified domain name that forward-resolves back to the droplet's IP.

My droplet was named keepbreath.ing, so DigitalOcean had set its PTR to keepbreath.ing. But keepbreath.ing is Cloudflare-proxied, which means any DNS lookup for that name returns a Cloudflare address rather than my droplet's IP. A receiver running the check "does this IP's reverse-DNS name forward-resolve back to this IP?" got a mismatch every time, and that mismatch is what RDNS_NONE means.

I couldn't rename the droplet to some arbitrary domain and have the check pass, because the apex is proxied through Cloudflare. The only name that forward-resolves straight to the droplet is mail.keepbreath.ing, which I'd left unproxied. So I renamed the droplet from keepbreath.ing to mail.keepbreath.ing through the DO API. The rename updated the PTR automatically. There was no downtime and no reboot, and propagation took a few minutes.

I re-ran mail-tester, which came back with 10 out of 10 and no RDNS_NONE ding.

Renaming the droplet to mail.keepbreath.ing fixed the reverse DNS problem, but I wasn't happy leaving the whole box named after its mail role when the same droplet still hosts the site itself. That gave me an obvious next project: spin up a second droplet, migrate the site to it, and let the original box stay dedicated to the mail server and (eventually) the Flask backend. DO droplets are cheap enough that I can afford to run a second one, and the split gives me a clean separation between the public web front and the services running behind it. Really I'm treating this whole site as a long-running platform for hands-on learning across web development, hosting, and the various ways servers and clients talk to each other. The plan is to keep building it out over time, adding functionality that gives me an excuse to learn something new each time. Splitting the site off from the mail server is the first of those experiments.

Step 4: telling Gmail to use it

In Gmail's settings I went to Accounts and Import, then Send mail as, then Add another email address. I entered contact@keepbreath.ing, gave mail.keepbreath.ing:587 as the SMTP server, checked the TLS box, and pasted the SASL credential from the offline password manager. Gmail sent a verification link to contact@, which forwarded through Cloudflare into the same Gmail inbox. I clicked through it.

Now contact@keepbreath.ing is a selectable identity in Gmail's From dropdown. Anything I send from that identity goes out through my own SMTP server, gets DKIM-signed on the way, and arrives at the recipient as if it had come directly from contact@keepbreath.ing. My Gmail address isn't in any header the recipient can see.

I sent one final test from Gmail-as-contact@ to mail-tester, and it came back at 10 out of 10 on the actual path I'll be using in practice.

What Gmail did with the first messages

The very first test message I sent to my own Gmail account (before the PTR fix) went straight to spam. This wasn't a surprise. SPF, DKIM, and DMARC all passed in the Show Original view, but a brand-new sending IP from a random droplet doesn't get inbox placement, and I knew that going in. Reputation takes time to build.

What I was really watching for was the retest after the PTR fix. When I sent that one, Gmail briefly held it with a 4xx "try again later" response before accepting it a few minutes later. That's greylisting: the receiver refuses the first delivery attempt with a temporary failure code and waits to see whether the sender comes back. Postfix's default behavior is to retry deferred deliveries on a backoff schedule, so my server tried again a few minutes later and Gmail accepted it. The message landed in the inbox with all three authentication checks green in Show Original, and that was the moment I knew the finish line was in view. Everything else was going to be time and consistent sending.

The greylisting isn't a failure. It's a normal check on a first-time sender, and my server responding to it correctly is one small piece of the reputation Gmail is watching for.

I also noticed something about outbound port 25 on new DigitalOcean droplets. Community forums and many tutorials will tell you DigitalOcean blocks outbound 25 on new droplets by default. Mine wasn't blocked, but my droplet has been up for about a year and a half, and DigitalOcean lifts that restriction on accounts and droplets they've had time to observe behaving cleanly. If your droplet is new, you'll probably need to request the block be lifted or wait until your account has aged in.

This site used to be Hugo behind Caddy on a DigitalOcean droplet. Now it's hand-coded HTML behind nginx on the same droplet.

Why nginx, when Caddy was already sitting right there

Caddy is easier. It does automatic HTTPS, and I had a half-built Caddy setup on the box already. I went with nginx because it's the tool used everywhere in networking and security work, and I want to know it.

The nginx config itself was about two hours of work. The pieces around it took longer: TLS through Cloudflare, locking the origin down, and staging tests between environments.

Building it in layers

The first version was plain HTTP on port 80. Events block, http block, one server block. Inside the server block: include mime.types so browsers got the right Content-Type, and try_files $uri $uri/ =404 to fall through cleanly:

events {}

http {
    include       /etc/nginx/mime.types;
    default_type  application/octet-stream;

    server {
        listen 80;
        server_name keepbreath.ing www.keepbreath.ing;

        root  /usr/share/nginx/html;
        index index.html;

        location / {
            try_files $uri $uri/ =404;
        }
    }
}

That was the whole config at that point. No gzip, no security headers, no TLS. Gzip came next, then security headers, then TLS, then the firewall. Each layer was tested before the next went in.

That mirrors real deploy practice. Every break has an obvious cause because only one thing has changed since the last known-good state. Batch a dozen changes into a single deploy and the same break sends you back through all of them to figure out which one caused it. I was deliberately practicing that discipline here.

Locally I ran nginx under podman, not Docker. I'm on Fedora Kinoite, which is immutable, and installing Docker on an immutable OS is fighting the system for no reason. Podman runs the same OCI images and reads the same compose files. It has some Fedora-flavored quirks (SELinux wants a :z on volume mounts, and it wants the fully-qualified image name where Docker assumes docker.io), but those are one-line fixes.

Rootless podman published the port on IPv4 only, and localhost on this box resolves to IPv6 ::1 first, so curl localhost:8090 came back empty. curl 127.0.0.1:8090 worked immediately.

Security headers, and the Google Fonts trap

Once the site was serving, I added the security headers, all with the always flag so they get sent on every response including errors. The set was X-Content-Type-Options: nosniff, X-Frame-Options, Referrer-Policy, Permissions-Policy (set to disable camera, mic, and geolocation), and Content-Security-Policy.

For the CSP I built the policy from what the site loads, not a generic template. That meant reading my own source: no inline scripts, no inline styles, no inline event handlers. That let me write a strict policy with no unsafe-inline in it anywhere. Ten minutes here. On any template-generated site it would have taken much longer.

One trap in setting this up: Google Fonts loads from two different hosts. The stylesheet comes from fonts.googleapis.com and the font files come from fonts.gstatic.com. If you allow only the first, the CSS loads and the fonts silently fail. The browser gives you a CSP violation that reads like the font files are being blocked, because they are, because you told it to. You need style-src to allow googleapis and font-src to allow gstatic. The final directive:

add_header Content-Security-Policy "default-src 'self'; script-src 'self'; style-src 'self' https://fonts.googleapis.com; font-src 'self' https://fonts.gstatic.com; img-src 'self'; connect-src 'self' https://api.github.com; frame-ancestors 'self'; base-uri 'self'; form-action 'self'; object-src 'none'" always;

I left HSTS off at this stage. Forcing HTTPS from a header before the site can serve it locks the browser into a broken state. HSTS only makes sense once TLS is proven.

TLS behind Cloudflare

Cloudflare fronts this site, so the TLS story has two legs, and the second one is easy to misconfigure. The connection from the browser to Cloudflare needs a public certificate, which Cloudflare handles. The connection from Cloudflare to my origin server needs a certificate too, but it can be one that only Cloudflare trusts. That is what a Cloudflare Origin Certificate is: valid for fifteen years, trusted only by Cloudflare, useless to any other client. Cloudflare is the only thing that should be reaching my origin anyway.

I generated the origin cert from the Cloudflare dashboard, covering the apex and the wildcard. Put the cert and key in a certs directory on the droplet, chmod 600 on the key, added the certs directory to .gitignore so the private key can't be committed by accident. Kept an offline backup of both files as their own separate files. The TLS config was two server blocks. Port 80 became a bare 301 up to HTTPS. Port 443 did the actual serving with http2, TLS 1.2 and 1.3, the Cloudflare origin cert, and HSTS at a deliberately short max-age=300 for the rollout:

server {
    listen 80;
    server_name keepbreath.ing www.keepbreath.ing;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    http2 on;
    server_name keepbreath.ing www.keepbreath.ing;

    ssl_certificate     /etc/nginx/certs/origin.pem;
    ssl_certificate_key /etc/nginx/certs/origin.key;
    ssl_protocols       TLSv1.2 TLSv1.3;

    add_header Strict-Transport-Security "max-age=300; includeSubDomains" always;
}

The short window meant I could unwind quickly if something was wrong.

I keep an environment file outside the repo for a couple of values my tooling reads at startup. When I generated the origin cert, I pasted the certificate and the private key straight into that file, like CERT=<the whole PEM block>. That file gets sourced as a shell script, so the shell tried to run the pasted PEM as commands and the tooling fell over with a wall of errors. Nothing leaked, because the file lives outside the repo. The lesson is small and permanent: a sourced env file is KEY=value only. Certificates and keys go in their own files.

I staging-tested the whole TLS setup on non-live ports (8443) before touching 443, because the live Hugo site was still up on 80 and 443 and I was not touching that until the new setup was proven from outside the box.

The cutover, and locking the origin down

The cutover itself was uneventful, which is what staging is for. Stopped the Hugo container so it released ports 80 and 443, switched the nginx compose file to publish on those ports, brought nginx up. Flipped Cloudflare's SSL mode from Full to Full (strict) at the same moment, so Cloudflare now validates my origin certificate end to end instead of accepting whatever cert the origin presents. Plain Full is the trap where the origin cert is never checked, which makes it useless.

I kept the old Hugo image on the box instead of deleting it. Retiring a container while keeping its image is a cheap rollback. If the new site had misbehaved, one command would have brought Hugo back.

One hole remained. The origin was answering on 80 and 443 for anyone on the internet. Cloudflare was fronting the site, but if someone found my droplet's IP, they could hit it directly and bypass Cloudflare's WAF and DDoS protection entirely. The fix is to allow inbound 80 and 443 only from Cloudflare's own IP ranges.

I did this with a DigitalOcean Cloud Firewall, applied at the edge before traffic reaches the droplet. Not ufw on the box. Docker writes its own iptables rules that bypass ufw, so if you rely on the host firewall for container ports, you have a firewall that reads correctly and quietly does nothing. With doctl, pulled Cloudflare's published IP ranges from their API, wrote an inbound rule allowing 80 and 443 only from those ranges, left SSH open so I didn't lock myself out:

doctl compute firewall create --name keepbreath-cf-only \
  --inbound-rules "protocol:tcp,ports:80,address:173.245.48.0/20,address:103.21.244.0/22,..." \
  --inbound-rules "protocol:tcp,ports:443,address:173.245.48.0/20,address:103.21.244.0/22,..." \
  --inbound-rules "protocol:tcp,ports:22,address:0.0.0.0/0,address:::/0"

Then I tested from three angles. The site loaded through Cloudflare. SSH still worked. A direct HTTP request to the origin IP failed with HTTP 000 instead of serving the site. A firewall you don't test from the outside is a guess.

Raising HSTS, and a Docker inode gotcha

With HTTPS proven stable, I raised HSTS from the 300-second rollout value to a full year. Edited nginx.conf, pushed the change, pulled on the droplet, ran nginx -s reload. Ran curl -I against the site to confirm.

max-age was still 300.

Ran reload again. Still 300. Checked the config file inside the container. Definitely the new value. Reload was completing without errors. The header was old.

The cause is a subtle Docker behavior. I had bind-mounted the nginx.conf as a single file. When you mount a file into a container, Docker resolves that mount to the file's inode at container start. git pull does not edit files in place. It replaces them with new files, which means a new inode. The container was still pointed at the original inode. That file no longer had a directory entry, but it still existed because the container had it open. nginx reloaded honestly. It just reloaded the config it could see, which was the stale one.

Reload alone didn't take. docker restart did:

git pull
nginx -s reload
curl -sI https://keepbreath.ing | grep -i strict
# strict-transport-security: max-age=300; includeSubDomains   <- still stale!

docker restart keepbreath
curl -sI https://keepbreath.ing | grep -i strict
# strict-transport-security: max-age=31536000; includeSubDomains

The real fix is to bind-mount the config directory instead of the single file, so an inode swap on the file inside no longer matters. That's on the backlog now.

What I learned

Curl looked broken because localhost resolved to IPv6 while podman had only bound the port on IPv4. A pasted certificate became a shell command because I put it in a file that got sourced. A squash-merge left git branch -d complaining a branch wasn't merged. Docker served a stale config because the bind mount was pinned to an inode git pull had orphaned. Docker's iptables writes bypass ufw entirely, which is why the firewall had to live at the DO edge.

The current box is running end-of-life Ubuntu and needs to be replaced. There's a saying you'll hear in DevOps circles: "cattle, not pets." The phrase was coined around 2011 by Bill Baker at Microsoft and popularized by Randy Bias of CloudScaling. Pets are servers you name, feed, and nurse back to health when they break. Cattle are numbered, interchangeable, and replaced when they fail. The point of keeping your infrastructure in code is to move a server from the first category to the second.

Because my whole stack now lives in git, this box is cattle. The next post is standing up an identical stack on a fresh LTS droplet and cutting DNS over to it.

I made Pong in Python. It's the game everybody makes first, which is why I picked it. I wanted practical experience on something small enough to actually finish, so I started it on my own outside of class.

The plan going in was to keep iterating on it until it was polished. This post covers the first stretch of that, from a working Pong to one that's worth playing.

The basic version worked and it was boring. Nothing broken about it. Ball moved, paddles moved, score counted, somebody won. The problem was that there was nothing to do. The ball hit a paddle and reversed, which meant both players could stand still, tap a key when it got close, and rally like that until they got tired of it.

The physics

I made the contact point on the paddle set the return angle and the return speed.

offset = (ball.y - paddle_center) / (paddle.height / 2)

speed_y = offset * 6 + paddle.dy * 0.4
speed   = 4 + abs(offset) * 5 + abs(paddle.dy) * 0.7
speed   = min(speed, 16)
speed_x = direction * speed

So offset runs from about -1 at the top of the paddle to +1 at the bottom, with 0 dead center. Take the ball in the middle and it comes back slow and flat. Take it out near the tip and it comes back fast and steep.

So now you're aiming with the paddle. The middle is the safe place to meet the ball and it keeps the rally alive. The tip is where the dangerous shots come from, and it's also the part of the paddle you can miss with.

The paddle.dy in both lines is the paddle's own motion at the moment of contact. If you're sweeping when you connect you add pace regardless of which way you're moving, and you add angle in the direction of the sweep. Brush upward and the ball leaves upward.

A corner hit while sweeping hard is the whole game. That's how you score. Against the computer it's close to the only way you score, because anything softer gets read and sent back at you.

Which is why the speed is capped at 16. The ceiling isn't there to protect the computer, it's there to protect you. Uncapped, that same shot works just as well coming the other direction, and on HARD you end up facing balls that no human hand is getting to. The window is narrow. Fast enough that a rally has some threat in it, slow enough that a player who reads the shot can still get there.

Then the ball got stuck in the paddle

This one needs some setup, because the bug doesn't make sense until you know how the game actually moves.

The ball doesn't slide across the screen. Sixty times a second the program wakes up, adds the ball's speed to its position, checks what it's touching, and draws the result. The ball is teleporting. It's just teleporting in steps small enough that your eye reads it as motion.

My collision check was one idea. If the ball's box and the paddle's box are overlapping, flip the horizontal speed and send it back the other way.

At four pixels a frame that holds up fine. The ball only ever dips a few pixels into the paddle before it gets turned around, and by the next frame it's clear.

At sixteen it falls apart. The ball can land most of the way inside the paddle in a single jump. The code sees the overlap and flips it. Next frame the ball has only backed out sixteen pixels, and if it landed deeper than that, it's still inside the paddle. So the code sees an overlap again and flips it a second time, back into the paddle. Then out. Then in.

The ball sat there and vibrated. I let it run for a good while because I wasn't sure what I was looking at.

So I made two changes. The ball only gets turned around if it's actually heading into the paddle, which leaves one that's already on its way out alone. And the moment it makes contact, I move it so it's sitting flush against the face of the paddle, which clears the overlap before the next frame ever looks at it.

Then it went straight through the paddle

Same root problem wearing a different hat.

I was working out which direction to bounce by comparing the paddle's position to the ball's. If the paddle was to the left of the ball, send the ball right, and so on. Reasonable, until the ball jumps deep enough in one frame that its center ends up on the far side of the paddle's center. Now the comparison says the paddle is on the right, so the code sends the ball right, straight on through and out the back for a point. It did exactly what I told it to do.

I fixed it by not asking. The left paddle is on the left half of the screen and it is never going to be anywhere else, so I read the side off the screen half instead of recalculating it from two things that are both moving.

Corners were a smaller version of the same thing. Fast diagonals kept sneaking past the paddle tips through a very short overlap window, so I ran the collision box six pixels past each end. The paddle still draws at its real size and the angle math still uses the real height. The tips are just a little more generous than they look. I'd rather have that than a game that's technically correct about six pixels while your best shot of the night goes through the wall.

The computer got very good at being bad

I didn't see this one coming at all.

My CPU worked the way you'd expect. Follow the ball, center the paddle on it, hit it back. Under the old physics that made a decent opponent. Under the new physics it made the worst opponent that can exist, because centering the paddle produces the slowest, flattest shot in the game.

I had built something that accidentally optimized for playing badly. Every rally turned into the computer lobbing soft floaters at me until I lost interest.

So I gave it a plan instead of a position. When you return the ball, the CPU looks at where your paddle is sitting and picks a spot on its own paddle that will send the ball to the opposite half of the court from you. You're up high, it strikes low. It's trying to make you run.

It picks a new target every single time you hit the ball. That's what makes it feel alive. A long rally becomes a string of different attacks instead of the same one on a loop, and when the ball is heading away from it, it stops shadowing you and drifts back toward center.

Forty lines or so. Completely different game after that.

Difficulty

DIFFICULTY = {"EASY": (5, 18), "NORMAL": (7, 30), "HARD": (9, 42)}

Each level is two values. The first is how fast the computer's paddle can move, and the second is how far toward the corner it aims when it swings.

EASY moves slower than you do and aims politely, so you can beat it by putting the ball where it isn't. HARD matches your paddle speed and goes for the edges. None of it touches the ball itself. What changes between the levels is how good the opponent is at playing.

I still can't beat it on HARD. I can score on it, which is how I know the level is winnable and not just a wall, but taking one all the way to fifteen would mean practice hours I don't have right now. That doesn't bother me. I'd rather the top setting be something I have to grow into than something I cleared the first night I built it.

The dumbest bug in the project

The win screen could be dismissed by any key at all. So if you happened to be holding a movement key at the moment the last point landed, which is exactly what you're doing during a final rally, it appeared and vanished inside the same frame.

The reason it took me so long to catch is that I almost never got there. Most of my testing stopped well short of fifteen points, because I'd notice something off, change it, and start over. And once the physics were tuned but before I'd added difficulty levels, I couldn't beat the computer at all.

The first game I ever played through to a win was on EASY, after the difficulty settings went in. I scored the fifteenth point, something flickered, and I was back at the menu. Locking dismissal to Enter and Space fixed it, and the second time I won I actually got to look at it.

Where it stands

One player or two, difficulty levels, an opponent that plays you, scoring, a win screen, a rematch. By any reasonable definition that's a finished game. It's just a plain one.

There are no image files and no sound files anywhere in this. Every single thing on the screen is a rectangle, a circle, or rendered text. I built it that way because I wanted it to be fun as plain shapes before I spent one minute making it look like anything. A game that plays well and looks plain is still worth playing.

So the next pass is making it look like something, and then seeing how much more game I can hang off a loop that already works:

  1. Space age pinball. Real palette, glow on the paddles and the ball, a tracer behind it, flashes when somebody scores.
  2. Bumpers out in the field to kick the ball around and pay out points.
  3. Multiball, or a different mode entirely, once the rest of it is finished.

That's the whole reason I started with Pong. It's small enough to finish and open enough to keep going.
