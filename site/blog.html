Notes from the Build▋

What I'm learning as I go, written down while it's fresh. Filter by tag.

There is a folder on my laptop that I have been calling the lockbox. It started as the place I put API keys because I didn't have a good way to store them, but it snowballed into a hackers wet dream. It grew with everything I built for the site and the home lab, and by this month it held three sudo passwords, the passphrase for the control plane's key, the mail credential, a Cloudflare DNS token, deploy keys, and an environment file holding six API tokens. Plain files, on an unencrypted disk, most of them readable by any process running as me. If the laptop were ever compromised, every piece of the site's infrastructure would go with it, and a few of those secrets reach into personal accounts as well. I knew that the whole time it was growing but time and attention kept me from fixing the problem.

The infrastructure I am building needs secrets handled properly. Agents and automation have to use them without a person pasting them in, and without one folder that hands out everything to whoever can read it. That is several projects, and this post is the first of them. It moves every secret a person uses into a vault on a server I run, and empties the lockbox of them. The next project is a secrets server for the machines. The backups project after that backs up this vault, which is the piece that makes it safe to depend on.

My ordinary passwords were a mess as well. Some were saved in Chrome, some in a Bitwarden account on bitwarden.com, some in Samsung Pass on the phone, and there was a file on the workstation desktop with a password in its name. I have never been good at password hygiene, because it is an unwieldy problem that gives me a headache. Since the vault for the infrastructure secrets is also a password manager, those went into it too.

By Sunday evening the lockbox held no human secret, every browser and the phone were filling passwords from the vault, and the laptop had no SSH private key on its disk. The login to the bastion comes out of the vault instead. It took one late night and the Sunday after it.

Why Vaultwarden, on its own VM

The secrets split two ways, and which side a secret is on decides where it lives. A person needs one unlock and frictionless fill everywhere, while a machine needs to prove what it is and receive only what it is allowed. Those are different products. This project is the human half, everything I type or paste myself. The machine half, deploy keys and tokens that a server reads unattended, is OpenBao, the open-source fork of HashiCorp Vault. A script I run by hand on the laptop can read a token from this vault while it is unlocked. A server's automation cannot, because that puts a personal vault in the path of a machine.

My first idea was to encrypt the lockbox in place and keep the folder. That would have fixed the plain files on disk and nothing else. It would still be one folder on one laptop, with no way for the phone or the workstation to use it, and no way for a server to fetch a machine secret without the laptop in the loop. A vault for the human secrets, and a secrets server for the machine ones, fits what the infrastructure needs. The folder gets emptied rather than hardened.

For the human half, Vaultwarden is a small open-source server that speaks Bitwarden's protocol. The official Bitwarden extension, phone app, desktop app and command line all work unchanged against it, pointed at my own server instead of Bitwarden's. That is the reason to pick it over staying on bitwarden.com, or moving to KeePassXC or pass. I already know the Bitwarden clients and they work everywhere I need them, and this way I get them on a server I own.

It runs on VaultServ, a small AlmaLinux 10 VM with one CPU and 3 GB of memory, on the Windows tower in my office that hosts my lab VMs. It has its own VM rather than sharing the one that already runs my monitoring, because a password vault should not share a fate with a box that gets rebuilt and experimented on. Nothing else will ever run on VaultServ, and it is reachable only over my tailnet. Tailscale builds a private network between my own devices, so the vault has no port on the home LAN and nothing on the public internet. My laptop, my workstation and my phone can reach it and nothing else can.

The trade for running the server myself is that the backups are mine to get right, and as of this post there are none. Bitwarden's hosted service would have handled that for me. I am taking the risk on for a short while, with the old stores left in place as the fallback.

Getting started...

The VM was built Saturday night. By the time it was patched and on the tailnet it was a bit after one in the morning, and the Vaultwarden work started from there. The first login was over Tailscale SSH, which means Tailscale checks that the connection comes from a device on my tailnet and there is no SSH key to manage.

Podman was not installed, which fit, since the VM build stops at a patched box on the tailnet. The container setup follows the three DigitalOcean droplets that run the site, step for step. Podman comes from the AlmaLinux repositories, and the container runs under a numbered account, keepbreath4, with a home directory and lingering turned on. Lingering means systemd starts that user's services at boot and keeps them running after the SSH session closes, so the container is that user's systemd service rather than a process tied to a login.

Rootless Podman also needs the account to own a block of subordinate user IDs, which are the host IDs that users inside the container get mapped to, and useradd hands one out on its own.

The droplet that serves the site needed a kernel setting, a sysctl, that lets an unprivileged user bind ports under 1024. This box gets by without it, since Vaultwarden listens on a high port bound to localhost and Tailscale fronts it, so the container user never needs a low port. One loosening fewer.

Vaultwarden 1.37.2 under Quadlet, and a health check that came back empty

The image is pinned by digest, the same way the bastion's runner image is pinned. A digest is the hash of the exact image contents, so vaultwarden/server@sha256:5d32... names one specific build and latest names whatever was pushed most recently. Pulling by tag and pinning by digest means an update is a change I make on purpose.

The container runs under Quadlet, which is Podman's way of describing a container as a systemd unit file. It lives at ~/.config/containers/systemd/vaultwarden.container in keepbreath4's home. The port is published on 127.0.0.1:8080 only, every Linux capability is dropped, and ROCKET_PORT=8080 tells Rocket, the Rust web framework Vaultwarden is built on, to listen there rather than on port 80. Vaultwarden's DOMAIN setting is the tailnet name it will be published under, set before the first account exists, because passkeys and attachment links embed it.

The data directory is a plain directory on the host at /srv/vaultwarden/data, mounted straight into the container from that path rather than kept in a Podman-managed volume. That was decided before the install, because a future backup job has to read it as an ordinary directory, and there is no backup job yet. Until there is, this directory is the only copy of every password, so the old stores do not get deleted at the end of this post.

First start:

     Active: active (running) since Sun 2026-09-13 01:36:20 CDT; 5s ago
     Memory: 32.9M (peak: 48.5M)

Then the health check five seconds later:

$ curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8080/alive
000

Status 000 from curl means it never got an HTTP response at all, and exit code 56 means the connection opened and then dropped. The service was active, memory was climbing, and nothing was answering.

The container log had the answer. On first boot Vaultwarden generates the RSA key it uses to sign login tokens, and on one CPU that took fifteen seconds:

[2026-09-13 06:36:21.494][vaultwarden::auth][INFO] Private key 'data/rsa_key.pem' created correctly
[2026-09-13 06:36:36.408][start][INFO] Rocket has launched from http://0.0.0.0:8080

There was nothing to fix. The second check answered 200. "Active" from systemd means the process started, and on a slow box that is not the same as ready.

The data directory listing showed the next thing to fix. The SQLite database and the signing key were mode 644, readable by any account on the box. This VM only has the two accounts I made, but that is the same mistake as the lockbox, so the directory got 700 and the two files got 600. The ls I ran straight after to confirm it said Permission denied, because it ran as keepbreath0 and the directory now belongs to keepbreath4 alone. That is the point, and sudo ls showed the modes.

Published as a Tailscale Service

The vault gets its name from a Tailscale Service, which is a name and address on the tailnet that belong to the service rather than to a machine. I defined it in the admin console first, because a host cannot advertise a name that does not exist yet. The name is vault and the endpoint is tcp:443. Tailscale assigned it its own 100.x.y.z address and the name vault.<tailnet>.ts.net, where the middle part is the random suffix every tailnet gets. Whichever approved host advertises the service answers at that address.

Then on the VM:

sudo tailscale serve --service=svc:vault --https=443 127.0.0.1:8080

That tells Tailscale to answer HTTPS on 443 with a certificate it issues for the name, and hand the traffic to the container on localhost. The first run opened a page to enable Serve on the node, a one-time click. After that the Service's Hosts tab listed vaultserv and I approved it. Approval is per host on purpose. It is what stops a stray machine on the tailnet from claiming the name.

Access on the tailnet is controlled by a policy file, and mine still carries Tailscale's default grant, which lets every device reach every other device. Replacing that is its own job and not a two in the morning edit, because a wrong line there cuts off every machine in the house. I added the explicit rule anyway, so the vault keeps working the day the wildcard goes:

{ "src": ["autogroup:member"], "dst": ["svc:vault"], "ip": ["443"] }

The autogroup:member source is the laptop and the phone, the devices logged in as me. Tagged servers are not members, so the bastion and the monitoring VM will not reach the vault once the wildcard is gone, which is correct. A server has no business in my password vault.

$ curl -s -o /dev/null -w "%{http_code}\n" https://vault.<tailnet>.ts.net/alive
200

The name, the certificate, the grant and Vaultwarden were all working from the laptop.

The extension on the workstation said "Failed to fetch"

I created the account in the web vault and installed the Bitwarden extension in Chrome on the laptop. It signed straight into my old bitwarden.com account instead of my server, because the server choice is a dropdown on the email screen, labelled "Logging in on", and it has to be changed to Self-hosted with the server URL before anything is typed. An extension that already holds a login shows the vault and never shows that screen. Logging out, then choosing the server first, worked.

On the workstation the same extension got as far as the password step and said "Failed to fetch". From a terminal there:

> curl.exe -s -o NUL -w "%{http_code}\n" https://vault.<tailnet>.ts.net/alive
000
> nslookup vault.<tailnet>.ts.net
Server:  UnKnown
Address:  192.168.x.x
*** UnKnown can't find vault.<tailnet>.ts.net: Non-existent domain

The name was going to the LAN's DNS server, which has never heard of .ts.net. The Tailscale client on the workstation had "Use Tailscale DNS" switched off. The network path was fine, since curl --resolve with the Service's address returned 200. Only the name was broken. The fix was tailscale set --accept-dns=true, which adds a split route so that .ts.net names go to Tailscale's resolver and everything else stays on the LAN server. After that curl by name returned 200 and the extension logged in.

Running nslookup again still said the name did not exist, and that is a Windows quirk rather than a problem. Windows keeps per-domain DNS rules in a table called the NRPT, which is what Tailscale writes its split route into, and nslookup ignores that table and talks to one server directly. Tailscale's DNS documentation says the same. The browser and curl go through the system resolver and see the route, and Resolve-DnsName in PowerShell is the test that does too.

By then it was after two in the morning. The server was up and the account existed with nothing in it, and I went to bed.

Sunday, and every store into the vault

I picked it up around ten on Sunday morning at the import step. Vaultwarden's web interface has Tools, Import data, with a format dropdown, and the order I had decided on beforehand was the old Bitwarden vault first, then the browsers, then the plain files and SSH keys last, so the riskiest data moves after the process is proven on the rest.

The Bitwarden export came out of bitwarden.com as JSON and went in as Bitwarden (json) without complaint. I had not paid attention to which export I asked for. There is a password-protected one and a plain one, and I had the plain one, which meant every password I had was in clear text in ~/Downloads for about five minutes. I shredded it with shred -u straight after.

The Chrome and Firefox exports are only ever CSV, so those were clear text by design, imported as Chrome (csv) and Firefox (csv) and shredded the same way. Zen, the browser I had been meaning to make my daily one, turned out to hold one password, which says how little it had actually been used for logging into anything.

Once it was logged in, the extension offered to make itself Chrome's default password manager, and after that Chrome's settings page shows "Offer to save passwords and passkeys" switched off, with "Bitwarden Password Manager is controlling this setting" underneath. Chrome will not turn its own saving back on while the extension holds that setting.

Firefox has no equivalent. Bitwarden's help page says to turn off Firefox's password saving by hand, which is a checkbox under about:preferences#privacy, and a Firefox update or a stray click can turn it on again. I turned it off on both machines and will have to keep an eye on it.

Chrome's old password store is still full and still synced to my Google account. It gets deleted once the vault has a backup, and not before.

Signups on the server stay open. The people I live with should be able to make their own account if they want one. Each account is its own encrypted vault under its own master password, so sharing the server shares nothing else. How their phones and laptops reach it is a later question, since they are not on the tailnet.

Unreachable...

On the phone, over mobile data, https://vault.<tailnet>.ts.net/alive did not load. The Service's address did not load. The VM's own tailnet address did not load either. Chrome on the phone said the address was unreachable. The Tailscale app showed connected, and from the workstation tailscale ping to the phone got pong from phone via DERP(dfw). The phone had answered, and the reply had come back through Tailscale's relay in Dallas.

I checked Private DNS, the "Use Tailscale subnets" switch and the client version first, and all three were fine. The clue was the word "unreachable". If the name or the route had existed and the server were down, Chrome would have said "refused" or "timed out", because the packets would have had somewhere to go. "Unreachable" means Android had no route at all for Tailscale's 100.x addresses. The app was signed in, and it answers Tailscale's own pings itself, but the VPN tunnel it is supposed to hold open was not up. Disconnecting and reconnecting in the app made Android rebuild the tunnel. The vault loaded, and the Bitwarden app logged in against the server.

Samsung Pass, with no importer

Samsung Pass exports a .spass file, and the Bitwarden app cannot import it, on the phone or anywhere else. I sent it to the laptop with Taildrop, which is Tailscale's file transfer between a person's own devices, and looked at the format.

The format is documented by the open-source converters people have written for it, such as spasstocsv. The file is base64 of a 20-byte salt, a 16-byte initialisation vector (the random starting block the cipher needs), and then the data encrypted with AES-256-CBC, the key derived from the export password by PBKDF2-SHA256 at 70,000 rounds. PBKDF2 is the standard way to stretch a password into an encryption key by hashing it many thousands of times. I did not want to run somebody else's converter against a file of all my phone's passwords, so I wrote a ten-line script that used only Python's standard library and openssl. Inside was a set of semicolon-separated tables with base64 fields, one table each for logins, cards and addresses.

Out came 47 logins, 25 for websites and 22 for Android apps, which Samsung stores as android://<signature>@<package>. I wrote them as a Chrome-style CSV and imported that as Chrome (csv), with the app entries named app: <package> so they read in the vault list. Bitwarden's Android autofill matches on the package name, so the odd-looking address is the useful part. The one card and one address did not carry over, since the CSV importer only takes logins. They go in by hand. The .spass file, the decrypted tables and the CSV were all shredded afterwards.

That finished the phone. The Bitwarden app is pointed at the server, set as the autofill service, with biometrics on.

The SSH key comes out of the vault

The SSH keys went last, after everything else had proven the process. The Bitwarden desktop app can act as an SSH agent, which means it holds the private key in the unlocked vault and answers ssh's request to sign a login challenge, so the key never has to exist as a file. This is the same job ssh-agent does on the bastion, done by the vault.

The desktop app is Bitwarden 2026.8.0 from Flathub, logged in against the server. The agent switch is under Settings, reached on Linux with Ctrl and comma because the menu bar is hidden. I copied the laptop's key to the clipboard with wl-copy < ~/.ssh/id_ed25519, made a new SSH key item, chose Import key from clipboard, and cleared the clipboard. The key is in OpenSSH format, so it went straight in.

The app is a Flatpak, the sandboxed way of installing desktop apps on Linux, and its agent socket is under the app's data directory, not in the home directory where a native install would put it:

export SSH_AUTH_SOCK=$HOME/.var/app/com.bitwarden.desktop/data/.bitwarden-ssh-agent.sock
ssh-add -L
ssh-ed25519 ... laptop id_ed25519

The ssh-add -L command lists the public keys the agent is offering, and there was the laptop key, served from the vault. For the real test I moved the private key file aside, so ssh could not possibly be reading it, and logged into the bastion:

mv ~/.ssh/id_ed25519 ~/.ssh/id_ed25519.moved
ssh -o IdentitiesOnly=no bastion hostname
control.keepbreath.ing

The IdentitiesOnly=no override was there because the laptop's SSH config sets IdentitiesOnly yes and names the key file, and I did not want the config to hide whether the agent was answering. It turned out not to be needed. Plain ssh bastion works with the file gone, because the config's IdentityFile still points at the key's name and the .pub half is enough for ssh to pick the matching key out of the agent. The socket export went into ~/.bashrc, and the moved-aside key got shredded.

The workstation's key from the lockbox went the same way. I imported it, moved the file aside, tested by tailnet address, got WSOPTICON1 back, and shredded it, along with a Kate swap file that had sat next to it since July. The ~/.ssh directory now holds id_ed25519.pub and no private key.

Emptying the lockbox

This is the step the whole project was for. The lockbox held ten files of human secrets, the ones listed at the top of this post plus a few spent or retired items. Copying each value by hand through the clipboard would have been one chance per value to paste it somewhere wrong, so I wrote a short Python script that reads the lockbox files and writes a Bitwarden JSON import. The import is a folder called Infrastructure with seven items, each named for what it unlocks, the username filled in, and a note saying which file it came from. The six API tokens went into one secure note as hidden custom fields, named exactly as the variables in the environment file were, so the Bitwarden command line can fetch them by name later. I imported it, confirmed seven items in the vault, and shredded the import file.

Then the ten source files were shredded. What is left in the folder is machine secrets and artifacts, which means the origin certificate and key, a mail server tarball, router backups, and two connection files.

Nothing on the laptop can source secrets.env any more. The scripts I run by hand that need a token will read it from the vault through bw, the Bitwarden command line, and that is not set up yet.

That leaves the lockbox holding only the machine half, and that waits for the secrets server. That is the next project.

A reviewer on the pull request for this post pointed out that the runner design below left the repository-admin token readable by any job the runner ran: the container that registered the runner was the container the job ran in, and the token stayed mounted at /run/secrets/ the whole time. That is fixed. The runner now registers with a just-in-time config minted on the host before the container starts, good for exactly one job, and the admin token never enters a container. A bastion host is a server whose only purpose is to be the front door for administrative access. You log into it, and from there you reach the machines that actually do the work. This post is that work.

Reading the boxes before touching anything

I started on Labor Day, late. The day had gone to my Linux class and a family gathering, and I got to the laptop that evening after putting the migration post up. Before planning any of this I logged into all three boxes and dug around. Two weeks of running had moved things since they were built, and I did not want to plan a lockdown from memory. So the first evening went to firewalls, listening ports, jail lists and home directories, writing down what was there.

All three boxes were AlmaLinux 9.8 with SELinux enforcing, firewalld active, and fail2ban watching sshd and banning any address that failed to log in three times, for longer each time it came back. The control plane ran sshd and nothing else. It had no Ansible, no git, no podman, and not even tmux.

The three droplets share a private network, DigitalOcean's VPC at 10.128.0.0/20, which every droplet in a region gets by default and which was already carrying mail from the web box to the mail box on port 2587. Addresses on it cannot be reached from the internet, and the web and mail boxes accept SSH on it the same as on their public addresses. That is what makes a bastion possible: the workload boxes can drop port 22 from the public side and keep it on the private one, and the control plane, which keeps its public port 22, becomes the only way across. The one sshd setting a jump host needs, AllowTcpForwarding, is on by default, so the bastion itself needed no SSH configuration at all.

The cloud firewalls were otherwise tight. Ports 80 and 443 on the web box were open only to Cloudflare's published ranges. Port 2587 on the mail box was open only to the web box's private address. And port 22 was open to 0.0.0.0/0 and ::/0 on all three, which is the one port this project exists to close.

The sshd jail on the mail box was catching a steady stream of failed logins. By Wednesday, when I took the picture, it stood at 2,519 failures and 323 banned addresses. Nothing was ever going to get in that way, because SSH refuses passwords outright, but the noise makes the successful logins, the ones worth noticing, hard to find.

Then I looked at port 587 on the mail box. That is the submission port, the one Gmail logs into with a username and password to send mail as contact@, and it is open to the whole internet because Google does not publish the addresses it sends from, which the mail identity post goes into. It is the one port on any of the three boxes where a password can be guessed, and a guessed password would let someone relay mail as me. Running fail2ban-client status listed one jail, sshd. Nothing was watching 587. The mail log showed 1,306 connections to it, every client that identified itself was a scanner, and four of them had tried a password. Nobody was seriously working at it, but the watcher was on the port that cannot take a password and missing from the one that can. I added a postfix-sasl jail for it on Wednesday.

Why the deploy runs on the control plane

The deploy had to go through the control plane. That was the design from the day I split the stack across three boxes, because closing port 22 on the web box is the point, and the deploy is the one thing besides me that connects to it. The question was how, and the first two ways I could see were both bad.

The existing deploy ran on a GitHub-hosted runner, which is a throwaway Ubuntu machine GitHub spins up for each job. It wrote the deploy key to disk, connected to the web box over the public internet, ran the deploy script, and was destroyed. That connection is the reason port 22 had to be open to the world on the web box. Making that runner jump through the bastion would mean opening the bastion's port 22 to GitHub's whole changing address range, which defeats the point of having one. Leaving the deploy direct means the web box keeps its public SSH port, which makes the sentence in the title false.

A self-hosted runner needs only an outbound connection to GitHub. Put it on the control plane and the deploy reaches the web box over the private network, and nothing has to be let in from outside.

My repositories are public, though, and GitHub is pretty clear that self-hosted runners should almost never be used with them: anyone can fork the repo, open a pull request, and have their code run on the runner. That was not hypothetical. Someone had already forked keepbreath-contact-api in August and added a test, asserting that an expired ALTCHA token is rejected. It touched nothing but tests/, and it passed against main, so they had found a gap in my coverage rather than in my code. The next fork could just as easily open a pull request that runs something on a box inside my private network.

GitHub has a repository setting that separates reading from contributing: pull request creation can be restricted to collaborators while the repository stays publicly readable. That is what I wanted from public repos all along: employers can read the work, nobody contributes to it. The API field is pull_request_creation_policy, which I found by changing the toggle on one repo and diffing the two API responses. Useful trick whenever a UI switch does not tell you what it is called underneath. By then it was three in the morning on a holiday, with class again in a few hours, and I went to bed.

Key to get in, password to become root

The building started on Wednesday, between deliveries at work. Every administrative login to these boxes, mine included, was as root. Root login was key-only with passwords off, so it was not weak, but root does not say who. The log reads identically whether it is me at the keyboard, Ansible pushing config, or someone holding a stolen key.

So I created keepbreath0 on the web and mail boxes, the same name on both so Ansible logs in as one user everywhere. It is numbered rather than named for its role, like the container accounts keepbreath1 through 3, because an account name should not advertise what a machine does.

A lot of Ansible tutorials give the account Ansible logs in as passwordless sudo, so playbooks can run unattended. I did not, and on a box that faces the internet I would not. The RHEL STIG, the US government's hardening baseline for Red Hat systems, requires that every sudo user provide a password, and Red Hat's Ansible hardening guide covers running without NOPASSWD for exactly that reason. Unattended runs are a convenience I do not need on three boxes. So keepbreath0 logs in with a key and becomes root with a password, two secrets doing two different jobs. A stolen key does not give root, and a learned password does not give access. Root login gave both to whoever held the key. Ansible prompts for the password with --ask-become-pass rather than storing it, so the control plane holds no credential at all.

Installing a public key for a new account on AlmaLinux has two traps I knew from the last build. The authorized_keys file has to belong to the account, with mode 600 in a 700 directory. And because root created the file, SELinux tags it as root's, and sshd will not read a key file with the wrong tag until restorecon fixes the label. Get either one wrong and the login just fails, with nothing in the client output to say why.

The control plane gets its own key

The control plane came the same day. It had only ever been logged into, so it had an authorized_keys file and no private key of its own. Now it needed to connect out, to 10.128.0.3 and 10.128.0.4 across the private network.

Before generating anything I created keepbreath0 here too, and generated the key on the control plane itself, so the private half never exists anywhere else. Without an account here, the chain would have been root on the control plane driving named accounts on the other two, which throws away half the point of having them. Now it is keepbreath0 on the control plane using its key to reach keepbreath0 on the other two, and root appears nowhere except the moment sudo escalates.

The key is passphrase-protected, for the same reason NOPASSWD was rejected: one stolen thing should never be enough. Someone who gets root on this box and takes the key file has an encrypted lump. I confirmed the passphrase took rather than assuming it did, with ssh-keygen -y -P "" -f against the private key. That succeeds on an unencrypted key and fails on an encrypted one. It failed, which was the answer I wanted.

Then the public half went into authorized_keys on web and mail with >>. That one character is worth being awake for. A > on its own would have replaced the file and removed the laptop's own access to the account. The first ssh keepbreath0@10.128.0.3 hostname from the control plane came back web.keepbreath.ing, and mail the same way.

Ansible reaches all three

I started ssh-agent on the control plane and loaded the key into it with ssh-add. The agent holds the unlocked key in memory for the session and dies with it, so nothing is written to disk. That is a different thing from agent forwarding, which shares the laptop's agent with a remote box and lets anyone with root there borrow the key. Running an agent locally on the control plane does not.

ProxyJump from the laptop

There are two ways to reach a server that sits behind a jump host, and the difference between them is the decision this whole project rests on.

Agent forwarding shares your local SSH agent with the bastion, so the bastion can use your key to authenticate onward. Anyone with root on the bastion can reach through that shared socket and use your key to impersonate you on every machine it opens, for as long as your session is live. ProxyJump works differently. It tunnels your local SSH client's connection through the bastion to the destination, and your client authenticates to the destination directly. Your key never touches the bastion.

The laptop's ~/.ssh/config gained three Host blocks: bastion at the public address, and web and mail at their private addresses with ProxyJump bastion. The private address is the important choice, because 10.128.0.3 is unroutable from the laptop, so the only way ssh web can succeed is through the jump. With the public address, SSH would go direct today and I would never know whether the jump path worked. Each block also sets IdentitiesOnly yes, so no box is offered a key it should not see.

An ephemeral runner in a container

The runner runs from GitHub's own image, ghcr.io/actions/actions-runner, pinned by digest. A digest is a hash of the image contents, so it always means the same build. A tag like latest can be pointed at a different build tomorrow, which is not something I want happening to a container that holds a deploy key.

The runner is ephemeral. It deregisters from GitHub after every job, and each job gets a clean filesystem. That means something on this box has to fetch a fresh registration token from GitHub every time the container starts, and the API call for that needs a token with the repository's Administration permission. There is no narrower permission that covers it to my knowledge, and Administration can also change branch protection and the pull request policy I set on Wednesday. So the ephemeral design puts a repository-admin credential on the bastion, and because the container that registers the runner is the same container the job runs in, a workflow step could read that credential from /run/secrets/ while the job is running. That is the trade, and it is a bigger one than I would like. Registering outside the job container, so that only a single-use config ever reaches it, was the fix, and it is done; see the update at the top of this post. It is a fine-grained token of its own, scoped to the one repository with Administration and nothing else, so the audit log names this consumer and it can be revoked without touching anything of mine.

The token went into Podman's secret store for keepbreath3 rather than a file. The command podman secret create runner-registration-token - reads the value from stdin, so it never enters shell history either.

The start script trades the credential for a one-hour registration token, runs config.sh --unattended --ephemeral --replace, and hands off to run.sh. I ran the container by hand first, so a registration failure would be on the screen rather than in a journal:

podman run --rm -it --secret runner-registration-token \
  --userns=keep-id:uid=1001,gid=1001 \
  -v ~/runner/start.sh:/usr/local/bin/runner-start:ro,z \
  ghcr.io/actions/actions-runner@sha256:5036...ec97 runner-start

The keep-id:uid=1001 option maps keepbreath3 to uid 1001 inside the container, which is the image's runner user. Without it, files the runner writes and files I mount belong to different people.

Then I wrote the same thing as a Quadlet unit. Quadlet is the part of Podman that turns a short container description into a systemd service, so the container starts at boot and restarts on failure like anything else on the box. The unit mounts the runner's .ssh directory read-only so the deploy job can use the key, and it sets Restart=always, because an ephemeral runner exits after its one job and something has to bring up the next.

There is a catch here. Running systemctl --user from a sudo -iu shell cannot find the user's systemd instance, because a shell reached that way is not a login session. Lingering means the instance exists at /run/user/1000 regardless, so two environment variables point the shell at it. After that, daemon-reload generates the service and start brings it up.

A systemctl status happened to catch the container nineteen milliseconds in, and the process tree read:

curl -sS -X POST -H "Authorization: Bearer gith…

The header was being passed as a command-line argument, and the command line of any process is readable by every other process on the box. So for the second that request runs, the registration credential is sitting in the process list. Since curl can read a header from stdin with -H @-, the script now pipes the header in from printf and the token crosses a pipe instead. I reinstalled the script and restarted the service, and a new container came up and re-registered, which also proved the exit-and-restart cycle the ephemeral design depends on.

Hardening the one door left

The control plane is now the only one of the three boxes accepting SSH from the internet, so the last stretch was about that box knowing what happens on it. It went in the same morning, in the hour and a half after the doors closed.

I had found the same thing on the web box at the end of August, and again on the mail box two days earlier while setting up the jail on its submission port. All three boxes were built before I knew to do that, and this was the last one without it.

The fix is a drop-in, a small config file placed in /etc/systemd/journald.conf.d/ that the main journald config reads on top of its defaults, with Storage=persistent and size caps. Then comes systemctl restart systemd-journald, and then the part that matters, journalctl --flush. A restart alone migrates nothing, and the once-per-boot flush already ran hours ago when there was nowhere to flush to. Now journalctl --header reports files on disk, including a user-1001.journal, the first per-user journal this box has ever had. That is all three boxes with a journal that survives a reboot.

Session logging is two lines in /etc/sudoers.d/10-iolog, written with visudo -f so a typo cannot lock root away:

Defaults log_input, log_output
Defaults iolog_dir=/var/log/sudo-io/%{user}

Running sudoreplay -l immediately listed the first sessions, and sudoreplay keepbreath0/00/00/01 plays the transcript back. Since keepbreath0 can only become root through sudo, this captures essentially every administrative action on the box, and sshd already writes who connected, when, and from where to the journal, which now persists. Sending the journal off the box waits for a monitoring stack that does not exist yet.

The plan met the fine print

The plan was three AlmaLinux servers, and I wanted one of them to be the old droplet rebuilt in place, keeping the address so the reverse DNS record, the SPF entry, and the IP reputation all survived. Ubuntu is in the Debian family, AlmaLinux is in the Red Hat family, and there's an open feature request asking for exactly what I wanted to do, which is how I could tell the answer was no.

A reserved IP on the mail box would have created a subtler problem. Reading the old box before touching anything

Before installing a package on a new box, I spent an afternoon on the old one. Not to change anything, just to read what was actually there.

The mail configuration needed to go into cold storage before anything else. The whole rest of the stack is in git and rebuilds from a repository, but the mail server isn't. Nothing under /etc/postfix, /etc/dovecot, /etc/opendkim.conf, or /etc/dkimkeys is in a repo, and the DKIM signing key can't be regenerated identically (regenerating it changes what's in DNS, which changes what receivers verify against, which breaks every message signed with the old key that's still in flight). I archived all of it as a tar with --numeric-owner, so file ownership was captured by user ID and group ID rather than by name, verified the checksum on both ends, and put the archive in my offline lockbox.

The --numeric-owner flag would have caused a specific problem on restore. The archive stored the DKIM key as UID 111 and GID 117, which is what the opendkim account happens to be numbered on Ubuntu. AlmaLinux almost certainly numbers that account differently, and if I restored with --numeric-owner the key would land owned by whichever unrelated account happened to be 111 on the new box. OpenDKIM refuses a key it doesn't own, and Postfix then sends unsigned mail rather than failing loudly. The fix is to restore without --numeric-owner, then chown opendkim:opendkim explicitly. In the end I didn't restore the archive at all, because the mail server was rebuilt from the ISPmail guide from scratch on the new box.

Rootless containers under systemd

On the old box the site ran under Docker Compose. It worked, but every container ran as root. The compose file was a separate configuration format from everything else on the machine, and the containers' lifecycle was managed by Docker rather than by systemd like every other service on the box. The new box was a chance to build the architecture I'd been reading about rather than copying the one I already had.

The runtime is Podman, which I already run on my laptop since Fedora Kinoite comes with it pre-installed. Podman is a drop-in for Docker at the command line, and it can run containers rootless which is more secure. That means the entire container process tree runs as an unprivileged user on the host, with a private user namespace that maps container root to a range of subordinate user IDs. If something inside a container ever broke out, it would land as an unprivileged user with no access to anything the login account itself couldn't touch. Docker can be run rootless too, but it's not the default and takes more configuration.

The lifecycle piece is Quadlet. Instead of a docker-compose.yml, each container is described in a systemd unit file that Podman's Quadlet generator turns into a real systemd service at boot. The container starts at boot and restarts on failure the way any other systemd service does, and it logs to journalctl next to everything else on the machine. There's no docker compose logs and no separate lifecycle to manage.

The site's Quadlet unit ended up being twelve directives long. I validated it on the laptop before ever copying it to the box, using Quadlet's own generator, which prints the systemd service it would produce without creating or starting anything. That caught two things I'd otherwise have found at boot. The image reference needed a fully qualified registry name in front of it (docker.io/library/nginx:alpine@sha256:...), because a service starting at boot has nobody to answer an interactive registry prompt about which registry to use. The hand-written After=network-online.target line was doing nothing at all, because that target doesn't exist inside a user systemd instance. Quadlet injects its own wait service for the network in a user context, so my hand-written line was silently ignored. Either would have shown up as an intermittent boot failure on the box, and the laptop validation caught them before the file was ever copied over.

The mail box, from scratch

I rebuilt the mail server from scratch using Christoph Haas's ISPmail guide as the foundation, adapting it for AlmaLinux along the way. Copying the old configuration would have been faster, but it would have hidden the distribution-specific differences until they caused problems. Starting clean forced me to understand each part of the setup and make those changes deliberately.

One Postfix setting needed immediate attention. mynetworks defines which IP addresses Postfix treats as trusted SMTP clients. A client in one of those networks can relay mail through the server without authenticating, so the setting needs to be as narrow as possible. Postfix documentation describes those clients as having more privileges than ordinary clients, including the ability to relay mail.

On this server, the generated value included 165.245.128.0/20, a DigitalOcean public network shared by many customer droplets. If I had started Postfix with that value in place, any host in that range could have been treated as trusted and allowed to relay mail without a password. The service was not running yet, so nothing was exposed, but finding that value made the danger of inherited configuration very concrete.

I replaced the generated value with an explicit one:

mynetworks = 127.0.0.0/8 [::1]/128

That configuration trusts only connections originating on the mail server itself, over IPv4 or IPv6. It also became the reason I wrote every value in Postfix's identity and trust configuration explicitly instead of relying on defaults whose behavior can vary with version, compatibility settings, or network layout.

The rest of the identity block matches the previous mail-identity post, and I won't repeat that here. Two things about the Dovecot side were AlmaLinux-specific and would have broken a copied config. The shipped ssl = required line points at a certificate path that doesn't exist on this distribution, so Dovecot would refuse to start. I set ssl = no, which is correct here because Dovecot only opens a local Unix socket for Postfix to check passwords against, not a network port. The shipped 10-auth.conf also includes auth-system.conf.ext, which adds a Pluggable Authentication Modules (PAM) password database that stacks on top of the passwd file rather than replacing it. Without commenting it out, Dovecot would also have accepted any Linux account's password for mail login. A mail submission credential must not double as a way to log into a Linux account.

Found out my DKIM never mattered

Somewhere around the Dovecot work I spent a full evening on a wrong turn and it was really frustrating. My first pass carried OpenDKIM over from the old box, because that's how I'd set up mail signing in the previous post. Then I looked at the actual headers of a delivered contact-form message from the last week the old box was running, and OpenDKIM's signature was failing verification on every one of them. The reason was that Postfix signs a message with the OpenDKIM key first, then hands it to Brevo, and Brevo modifies the body by injecting an open-tracking pixel before sending it on. Any body modification after signing invalidates the signature, because the whole point of the signature is to detect body modification. What was actually carrying DMARC authentication for my domain was Brevo's own signature, using a key I publish in DNS on Brevo's behalf. My signature had been broken since the day I set it up and I hadn't noticed, because Brevo's signature was the one that mattered. Who knew email was so complicated?

Disabling Brevo's tracking would fix my signature, but the setting doesn't exist. Disabling tracking on transactional SMTP is a standing feature request on their forum, and the industry rule is that signing has to be the last step that touches a message, so I was signing before handing it to a relay that modifies it. That was a gut punch. All those weeks I thought I had my own mail signing dialed in, and it was Brevo doing the actual signing that mattered. What I built is still impressive, but I had wanted to do this without external services, and email is convoluted enough that I could not. That is exactly why I keep wanting to go deeper into security. I am tired of watching things get harder for everybody because a few people want to cheat the system.

The only reason I had left for keeping OpenDKIM at all was "for when the dedicated mail server might send directly one day." That was never going to happen. DigitalOcean blocks outbound port 25 on every droplet, and 465 and 587 as well since a policy update in March 2025, with the block described as permanent. Direct sending is impossible from a droplet, so a relay is permanent rather than something I pass through temporarily. OpenDKIM came off the mail box entirely, which deleted a package, a config file, and a mail filter hook.

The first real send from the new mail box wasn't uneventful. Postfix accepted the message locally with a 250 queued as response and then couldn't get it out. The log said SASL authentication failure: No worthy mechs found, which is a Postfix message so cryptic that I had to search around before I understood what was going on. Postfix's outgoing side performs logins through Cyrus SASL, whose mechanisms (PLAIN, LOGIN, and the rest) are separate plugin files that live in /usr/lib64/sasl2/. On this machine, only the anonymous mechanism was installed. Brevo requires PLAIN. On Debian and Ubuntu, the plugin packages arrive as a dependency of Postfix. On Red Hat, they don't. Installing cyrus-sasl-plain and restarting Postfix cleared it. Small workaround, and one of those little differences that is useful to know for next time. It is interesting how the different distros handle their packages, and it is something I hear about a lot when I am listening to Linux podcasts. For me, learning hands on and finding these little hiccups teaches me a lot more than everything working on the first try.

I tested the contact form by sending a message through it. I checked my Gmail and it had reached Gmail for the first time on the new infrastructure. Postfix accepted it, Brevo marked it delivered two seconds later, and Cloudflare Email Routing passed it on to the final inbox.

I had hoped the mail server would be finished much earlier. Instead, the first successful message arrived after several more days of rebuilding, testing, and fixing the pieces that had not behaved the way I expected. Seeing it land in Gmail really validated all the hard work I had put into figuring all of this out and banging my head against the keyboard for days. I don't regret it.

Three things the move broke

The contact API and Postfix had lived on the same server before the migration. When someone submitted the contact form, the API's background worker handed the message directly to Postfix through a local socket. The message never needed to leave the machine.

The new layout put the website and mail server on separate droplets. My plan was for the worker on the web server to submit mail to Postfix on the mail server through port 587 over DigitalOcean's private network. The mail server would accept those connections only from the web server's private address.

DigitalOcean's SMTP block also applied to private traffic. I suspected DigitalOcean's SMTP restriction might apply to private traffic as well, but I tested the normal submission port before designing around it. From the web server, a connection to the mail server's private address on port 22 completed in six milliseconds. SSH worked normally across the private network. The same test against port 587 did not return a refusal or an authentication error. It waited until it timed out. Port 25 behaved the same way.

That result narrowed the problem down. Both servers' firewalls allowed port 587 between their private addresses. The private network was working, as the SSH test showed. The mail server also answered immediately when I tested port 587 through its public address from my laptop. Postfix was listening, the firewall rules were correct, and the droplets could reach each other. The standard SMTP ports were the only part that failed.

DigitalOcean blocks SMTP traffic on ports 25, 465, and 587 by default to reduce spam and abuse. The restriction applied to traffic leaving the web server even when its destination was another droplet on the private network.

The original single-server design had not required a network connection between the worker and Postfix. Once I separated the API and mail server, the worker needed to submit messages across DigitalOcean's private network. I expected the provider's SMTP restriction to be a possible problem, and the tests confirmed it. Port 587 was unavailable between the two droplets, so I needed another private route to Postfix.

I left the public submission service on port 587 and added a second Postfix submission listener on port 2587. It bound only to the mail server's private interface, which meant it was reachable only through the private network. The service kept the same TLS and authentication requirements as port 587, but it used a port outside DigitalOcean's SMTP block.

Moving the Nginx configuration broke the old server during migration. The Podman deployment needed to mount the site's Nginx configuration directory rather than a single configuration file. The reason is covered in the "Docker inode gotcha" section of Migrating to nginx. A directory bind mount survives a git pull that replaces files, while a bind mount to one specific file does not.

To make that change, I moved nginx.conf into deploy/nginx/ in the repository. The new Podman deployment would mount that directory. The problem was that the deployment pipeline also pulled the same repository change onto the old server before the migration was complete.

The old server was still using Docker Compose. Its configuration still mounted ./nginx.conf as a single file. After the repository change, that file no longer existed at the path Docker Compose expected. When Docker tried to create the bind mount, it created an empty directory at the missing source path. The next configuration check failed with this message:

not a directory: Are you trying to mount a directory onto a file (or vice-versa)?

The site did not go down immediately because the running container was still using the original configuration file. It had opened that file before the repository update, and Linux kept the file's underlying inode available even after the pathname disappeared. Nginx continued serving the site from a configuration file that no longer existed anywhere in the working tree.

That was only temporary protection. The container could continue running, but it could not restart successfully. A reboot, an out-of-memory kill, or any normal container restart would have brought the site down because Docker could no longer mount the configuration file it expected.

I fixed the old server without undoing the repository change. On the old server, I created a symbolic link at the previous nginx.conf path that pointed to the new file inside deploy/nginx/. That gave Docker Compose the file path it still expected while letting the new deployment use the directory layout required by Podman.

Afterward, I ran nginx -t inside the existing container to verify that Nginx could load the configuration through the symlinked path. Once that succeeded, the old server could safely restart again. The symlink was a compatibility fix for a machine that was about to be retired, so I left it in place until the old droplet was destroyed.

Docker's internal DNS address did not exist under Podman. With the containers running and the site available on the new server, requests to /api/ still returned a 502 error. Nginx's error log showed the immediate cause. It was trying to resolve the upstream service name contact-api through 127.0.0.11 and timing out.

That address had worked on the old server because it is Docker's embedded DNS resolver. The new server used Podman, which handles container-network DNS differently. On this network, name resolution came from aardvark-dns at the network gateway address, 10.89.0.1. The containers were already using that gateway internally, so I updated the Nginx resolver to match the Podman network.

Before merging the change, I ran nginx -t inside the running container and confirmed that Nginx could resolve contact-api through 10.89.0.1. I also added a comment beside the setting. The gateway address is stable for the existing network, but changing it later would mean deleting and recreating the Podman network.

The configuration itself was a straightforward fix. Deploying it was a bit more involved.

At that point, the old server was still live and serving every real visitor. The deployment workflow ran deploy-site whenever changes were merged into main, but DEPLOY_HOST still pointed to the old Docker server. That was intentional at first. I had planned to update the pipeline after the DNS cutover.

The resolver change made that deployment order unsafe. Podman used 10.89.0.1 as the DNS resolver for its container network, but Docker did not provide a resolver at that address. If I had merged the change while the deployment pipeline still targeted the old server, the updated Nginx configuration would have been deployed to the Docker host.

Nginx would have started normally, so the site's regular pages would still have loaded. The failure would have appeared only when Nginx tried to reach the contact API. Requests to /api/ would have failed, and the contact form would have stopped working without an obvious error for visitors. It would have been another silent contact-form failure, this time caused by the deployment order rather than the earlier ALTCHA issue.

I repointed DEPLOY_HOST to the new server before merging the resolver change. That made the main branch safe to deploy again.

While I was correcting the workflow, I found one more problem in the verification step. It checked keepbreath.ing through public DNS, but public DNS still resolved to the old server. The workflow could deploy to the new server, test the old server by domain name, and report success even if the new deployment had failed.

I changed the verification step to test the new deployment directly rather than following the public DNS record. With the deployment target and verification target both pointed at the new server, a green workflow run finally meant the new server had actually received the change and was serving it correctly.

Five failures in a row on the deploy pipeline

I started working on the deploy script in the morning while sipping my coffee before heading to work. It was a busy day at work, so I didn't have any downtime for the deploy script. I picked it back up after I got home. It was past midnight when I finally got to the pipeline itself. I mistakenly thought repointing the deploy pipeline to the new box would take an hour. It took five fails and lots of banging my head against the desk.

The first died with hostname contains invalid characters. The value of DEPLOY_HOST I'd typed into GitHub's secret form had a stray character in it, apparently I had left a space at the end. It was one of those small details that feel like pulling teeth for no reason.

The next deployment completed successfully, but the workflow still failed during its curl verification step with exit code 28, which indicates that the request timed out. The deployment itself had worked. The failure came from a verification change I had made to avoid testing the wrong server.

Originally, the workflow verified the site by requesting https://keepbreath.ing/. That was not reliable during the migration because public DNS still pointed to the old server. I changed the command to use curl --resolve, which forced keepbreath.ing to resolve to $DEPLOY_HOST for that one request. In theory, this meant the GitHub Actions runner would test the server that had just received the deployment instead of whichever server public DNS happened to select.

The request never reached Nginx. Both servers allowed HTTPS connections only from Cloudflare's published IP ranges. A GitHub Actions runner connects directly from GitHub's infrastructure, not through Cloudflare, so the origin firewall dropped its connection attempt. curl waited until the connection timed out and returned exit code 28.

I moved the verification into the deployment script itself. After the files were deployed and the service was reloaded, the script ran the check locally against 127.0.0.1 on the target server. That avoided the Cloudflare-only firewall rule and verified the server that had actually received the deployment. It also remained correct after DNS cutover, unlike the public-DNS check and the direct connection from the GitHub runner.

The third deployment failed before SSH ever reached the server. The workflow printed two messages:

Load key "/home/runner/.ssh/deploy_key": error in libcrypto
Permission denied (publickey)

The second message sent me in the wrong direction at first. Permission denied (publickey) usually means the server rejected every key SSH offered, so I started looking at authorized_keys on the target server.

The first message was the important one. OpenSSH could not read the private key file stored by the workflow, which meant it had never attempted to authenticate to the server at all.

The workflow created that file with:

printf '%s' "$SECRET"

That command wrote the secret exactly as stored, without adding a trailing newline. OpenSSH refused to parse the resulting key file because the final newline was missing. I confirmed the cause locally by removing the trailing newline from a known-good private key and getting the same error in libcrypto message.

I added the missing newline and ran the workflow again. The next deployment failed with the same error in libcrypto message.

This time, the key had its final newline but its internal line breaks had been changed. A PEM private key is structured text. If its lines are collapsed into one line or converted to spaces while it is pasted into a web form or stored as a secret, OpenSSH can no longer parse it. I reproduced that failure locally by replacing the line breaks inside a known-good PEM key with spaces and receiving the same error.

At that point, I stopped storing the deployment key as raw PEM text. Instead, I Base64-encoded it before saving it as a GitHub secret. The encoded value was one uninterrupted line of text, so there were no PEM line breaks for a form or secret field to alter. The workflow decoded that value back into the private-key file immediately before it ran SSH.

I tested the encoding and decoding process locally first. The recovered key parsed correctly, and the next deployment could authenticate normally.

The fifth failure was base64: invalid input. The secret still held raw PEM, because the encoded value hadn't actually made it onto my clipboard when I copied it. I re-copied the encoded value, saved it back to the secret, and dispatched the workflow by hand rather than merging something just to trigger it.

The sixth run went green.

I could not see the later failures until I fixed the earlier ones. The workflow stopped at the first error it encountered, so each successful run revealed the next problem waiting behind it.

Two of the messages sent me toward the wrong diagnosis. Permission denied (publickey) sounded like the server had rejected the deployment key, but SSH had failed to read the key file before it attempted authentication. base64: invalid input looked like a decoding problem, but the value passed to the decoder was plain PEM text rather than Base64 data.

The logs showed where the workflow stopped, but the most obvious error was not always the useful one. I recreated each failure locally with a known-good key. Removing its final newline, replacing its internal line breaks with spaces, and trying to decode unencoded PEM text produced the same errors from the workflow. That made it possible to isolate what was wrong with the file at each stage and test the fix before running another deployment.

DNS cutover, and one real message

I updated four DNS records in Cloudflare as part of the cutover. The apex A record moved from the old server's public IP address to the new web server, and the staging subdomain was updated to point to that same host. The mail subdomain moved separately to the new mail server.

I also removed the ip4: mechanism from the domain's SPF TXT record instead of replacing it with the new mail server's address. Outbound contact-form messages leave the web server through Postfix, but Brevo handles the final delivery. Before sending the message onward, Brevo replaces the envelope sender with an address in one of its own bounce domains. Receiving mail systems therefore evaluate SPF against Brevo's sending infrastructure and that bounce-domain address, not against the IP address of either of my droplets. SPF checks the SMTP MAIL FROM identity and the IP address of the server making that SMTP connection.

I did not replace the old ip4: entry with the new mail server's address because the new server was not delivering mail directly to recipients. It passed messages to Brevo, and Brevo sent them from its own delivery infrastructure. Removing the old entry kept the SPF record focused on the servers that actually needed to be authorized.

The apex, www, and the staging subdomain all returned HTTP 200. The /api/challenge endpoint returned a real ALTCHA challenge payload with parameters, rather than the empty success it would have returned if the API had been silently misconfigured. Then came the test the rest of the build had been leading toward. I submitted the contact form from Chrome and watched the page confirm that the ALTCHA challenge had been accepted. The message reached my Gmail inbox at 9:03, about a second after I clicked Send.

The rest of the path happened behind the scenes. The request reached the API on the new web server, entered Redis briefly, and was collected by the background worker. That one message depended on every layer of the new setup working together. Cloudflare had to reach the web server through the cloud firewall, and the host firewall had to allow the connection through. Nginx then had to find the contact API through Podman's DNS, where the API could validate the ALTCHA challenge and place the message in Redis using the password loaded from its mounted secret.

Celery picked the message up from the queue and sent it across the private network to Postfix on port 2587. The TLS certificate had to validate against the hostname mapped inside the container. Postfix then relayed the message through Brevo, which delivered it through Cloudflare Email Routing and into Gmail.

# Wiring up the contact form, and everything hiding underneath

The website was the capstone project for my web programming class. At the time, the contact form was mostly a placeholder: it looked like a working form, but it was static HTML, and clicking Send did nothing. I knew I wanted to come back and make it real once I had more time.

I thought this would be a quick follow-up project. Build a Flask endpoint, take the form submission, send an email to myself, and finally bring the last unfinished piece of the site online.

It did not stay that simple. A public contact form is not just a message box with an email address attached. It is an internet-facing endpoint that has to handle malicious input, spam bots, rate limits, browser security rules, message queues, delivery failures, SMTP restrictions, and the trust checks that decide whether a receiving mail provider accepts a message or throws it away.

The finished version has validation, bot protection, nginx rate limiting, a Redis queue, a Celery worker, retry and recovery logic, container hardening, CI checks, and an authenticated relay for outbound mail. It took about a week and a half of evenings and a long weekend to get there.

Fall semester started in the middle of the work, so most of it happened during downtime at work or late at night after schoolwork. I had just come off my last programming class and was rusty enough that I had to look up how to write a Python dictionary on the first evening.

In the last post, I set up contact@keepbreath.ing as a two-way mail identity, with Gmail as the inbox behind it. That was the mail plumbing. This post is about connecting that plumbing to the form: taking it from a placeholder on a capstone project to a public-facing service that can accept a real submission and get it safely into my inbox.

The endpoint and its validation

The route is POST /api/contact. It takes three JSON fields (name, email, and message), validates them, runs the bot-defence checks, hands the message off to the mail path, and returns a small JSON response.

The validation itself is a straightforward function. It loops the three fields, rejects anything that isn't a string, strips whitespace, enforces length limits, and returns either the cleaned payload or a specific reason for the rejection. Two pieces inside it do the security work.

The email check is the first. My starting plan for it was a short regex, something like \S+@\S+\.\S+, and moving on with my day. Then I read the actual RFC 5322 grammar for an address, which runs to more than 6000 characters. Any short pattern either lets garbage through or rejects addresses that are actually valid. So I dropped the regex and used the maintained email-validator library instead. It runs the syntax check, enforces proper length caps, rejects domains without a dot, and hands back a normalized address. I turned off its DNS-deliverability check to keep requests fast, and stored whatever normalized form the library gave back.

The other is a check for carriage-return and newline characters in the name field. The name lands in the email's Subject header, and email headers are separated by newlines. A name containing a newline can inject a second header, and a hidden Bcc: line on that second header would turn one form submission into a spam blast. Python's EmailMessage has built-in protection against this, but the Python bug tracker has documented cases where it can be bypassed at the edges. So I reject \r and \n in the name field before any of that code even runs. Belt and suspenders.

Bot defence

Bot defence ended up being three layers, but the starting plan was one. A honeypot is a hidden form field a human never fills in because they never see it. A naive bot that just POSTs every field it finds will fill it in every time, and the API drops those submissions on the floor. About ten lines of code total. Then I read what bots actually do now, and realized a bare honeypot catches only the dumbest of them. It's the cheapest layer to build and the least sufficient on its own.

So mine has two more layers behind it: a cryptographic challenge, and a rate limit on the reverse proxy. Each catches a different kind of traffic, and any one alone is weaker than the three combined.

The middle layer took more thought. I looked at Cloudflare Turnstile first. It is free, privacy-friendly, and I was already using Cloudflare. For a site that only needed a CAPTCHA, it probably would have been the fastest answer.

This website is also where I learn by building. I wanted to understand what sits behind a public form: how a challenge is issued and verified, how the browser and API fit together, what the CSP allows, and where the abuse controls actually live. Dropping in a managed CAPTCHA would have solved the immediate problem, but it would have hidden most of the system I was trying to learn.

Turnstile would also have required adding Cloudflare's challenge domain to the site's Content-Security-Policy for its scripts and frames. I picked ALTCHA instead: an open-source proof-of-work CAPTCHA I could serve from my own domain, inspect in the browser, and connect directly to my own API.

The server hands the browser a small cryptographic puzzle at page-load, and the browser burns about a second of throwaway CPU solving it. The answer rides along with the form submission. A real visitor never notices the second. A spammer trying to hit the form thousands of times per second suddenly needs the CPU to do that arithmetic thousands of times per second, and the math makes it uneconomic. The CAPTCHA is invisible, and no human is ever asked to identify buses.

Because ALTCHA is self-hosted from my own domain, the Content-Security-Policy stays strict. I first picked ALTCHA's strict "external" build, thinking it would keep the CSP totally untouched. Then I read further and found that build needs a JavaScript bundler. Webpack, Vite, one of those. My site is hand-coded HTML with no build toolchain, and bolting webpack onto it to dodge a single CSP directive wasn't a good trade. I switched to the single self-hosted bundle and added one line to the policy: worker-src 'self' blob:. That lets my own JavaScript run inside a Web Worker, which is what does the puzzle-solving in the background, without opening the door to anything else.

I turned up a real CVE in the ALTCHA library while researching this: CVE-2025-68113, a challenge-splicing and replay flaw fixed in a recent version. I pinned to the fixed version. The attack pattern behind that CVE (an attacker solving one challenge and reusing the token for a burst of submissions) is also why the code keeps a single-use registry. Every accepted challenge is recorded in a small SQLite database with a UNIQUE constraint. Two workers can't accidentally both accept the same replayed token, because the second write fails.

The third layer, the rate limit, lives out in nginx and caps requests per client at five per minute with a burst of three. Client identity is keyed on Cloudflare's CF-Connecting-IP header, since all traffic reaches the origin through Cloudflare and $remote_addr would otherwise be a Cloudflare edge IP shared across every visitor.

Container hardening

With the app running locally, I put it in a container. The plan for this site is a set of services on separate droplets talking over a shared internal network, and the contact API is the first of them.

The Dockerfile itself is nothing exotic. It starts from a small Python base to keep the image small, and dependencies install in their own layer so a change to app.py doesn't trigger a full reinstall on every build.

The app runs as a non-root user called appuser, so a break-in inside the container doesn't hand out root, and a HEALTHCHECK line hits a small /health route with urllib so Docker can tell whether the app is answering, not just whether the process is running.

PYTHONUNBUFFERED=1 flushes Python's stdout after every line. My log lines are structured JSON going to stdout for later collection, and Python's default buffering means a crash can lose the log lines that would tell me why it crashed. With the setting on, every line flushes immediately, and docker logs shows the trail all the way to the fault.

I'd built a Stage 6 gate into the plan on purpose: before the image goes live, scan it for known vulnerabilities. I used Trivy, which reads what's inside a container image and cross-references it against public vulnerability databases.

I read the first scan wrong. I glanced at the tail of the output, saw no "critical" line on the last screen, and called it clean. Then I read the whole thing, actually taking in everything above the tail, and the image was carrying 186 known vulnerabilities, four of them critical and twenty-one high. Every single one was in the base operating-system packages or in pip's own build tooling. None were in my code or the libraries I'd chosen. The four criticals were all in perl-base. The headline one, a Perl regex-engine flaw, had been fixed upstream in Perl 5.43.10 but hadn't been backported into the Debian version I was on, so it was unpatchable in place.

The Debian scan was alarming because it showed how much software my small API had inherited without me really thinking about it. The container only needed to run Python, my application code, and its runtime dependencies. Instead, the Debian-based image brought along a full general-purpose userspace, including packages such as Perl, gzip, tar, ncurses, and login-related components that the contact API would never call.

None of that software was there because I chose it for the project. It came with the base image. Every extra package meant another dependency to patch, another set of known CVEs to track, and another component an attacker might be able to use if they ever got inside the container. The scan made the problem visible: I had built a small application on top of a much larger operating-system footprint than it needed.

I went looking for a slimmer base and switched to Alpine Linux. Alpine is built around musl and BusyBox rather than Debian's broader glibc-based userspace, so the Alpine Python image starts with far fewer packages installed. Alpine's minimal design is one reason it is commonly used for small container workloads, although musl can require extra testing when an application depends on native extensions.

The change showed up immediately in the next scan. Moving from the Debian-based Python image to Alpine dropped the known-vulnerability count from 186 to 3. The three remaining findings were in pip, setuptools, and wheel. Those packages were necessary to install dependencies during the image build, but the running API had no use for them. I removed them after installation, rebuilt the image, and Trivy reported zero known vulnerabilities in the final image at scan time.

The base-image swap still needed verification. Alpine keeps its CA-certificate trust store in a different location from Debian, and the application's outbound mail path depends on TLS certificate validation. A clean vulnerability report would not help if the container could no longer verify the mail server it needed to reach. I confirmed that all 119 CA certificates were present in the Alpine trust store, then sent mail through the normal path and confirmed TLS verification still passed.

That was one of the biggest wins in the project. I started by looking for a way to patch a noisy scan, then realized the better answer was to stop shipping software the application did not need.

By the time the clean scan came back, I was ready to be done for the day. I made dinner and had hot green tea with honey. The heat index outside was 115 degrees, and I had slept about four hours the night before.

I put everything under Git, pushed it to GitHub, and started laying the groundwork for CI/CD. The repository became the place I could deploy from, recover from, and use to track why each change happened.

I like having an outside set of eyes on pull requests, so I use GitHub Copilot for reviews. When I am deep in a build, I can get used to my own assumptions and stop noticing awkward parts of the design. A review gives me a reason to go back and look at them.

The problem was that I had just created the repository. There was no pull-request history yet, no established review loop, and no single previous change to inspect. Before I started building a pipeline around future pull requests, I wanted one full pass over the codebase I already had.

Taking the mail send off the request path

The biggest architectural change was decoupling the mail send from the HTTP request. In the first version the visitor's browser sat blocked on the POST while my server dialed the mail server, negotiated TLS, authenticated, and handed the message off. If the mail server was slow, the visitor's page was slow. If it was down, the request eventually failed and the message was gone.

So I moved the send off the request path. The API accepts the message, puts it on a queue, returns 202 Accepted immediately, and hands the actual send to a background worker. I built that with Celery (Python's most established background-job library) and Redis as the message broker between the web process and the worker. The Flask app validates, runs the honeypot and ALTCHA checks, and enqueues. A separate worker container reads the queue, builds the email, and sends it. Mail credentials live only in the worker's environment now, so the web process can't leak them even if it's compromised.

The textbook retry policy for outgoing mail says: retry transient failures (dropped connections, temporary server errors) with exponential backoff and jitter, and never retry permanent failures (auth errors, invalid addresses, bounces from the recipient's server). The reason not to retry permanents is that in normal mail, a permanent failure means a bad recipient address. Bombing a mail server with mail it's already refused hurts your sending reputation, and there's no point anyway. So my first design had a "dead letter" bucket for permanent failures: log the failure, drop the message, move on.

But every message this system will ever send goes to one address that I control. A "permanent" failure in that shape isn't about the message being undeliverable to the recipient. It's always about my own configuration being wrong: a rotated SMTP password, a misrouted forwarding rule, an expired certificate. Fix the configuration and the same message goes through. There's no such thing as a permanently undeliverable message when every message goes to you. The dead-letter bucket that said "give up on this one" was just wrong for this system.

The cleaner model is a Redis shelf and a scheduled sweep. A message that fails goes on the shelf. Every few seconds a background sweep re-drives the shelf back through the send queue. Failed messages land back on the shelf and try again on the next sweep. The transient-vs-permanent distinction now only decides one thing: whether to burn five fast retries first (for something that might resolve itself in seconds, like a dropped connection), or skip the fast retries and go straight to the shelf (for something that won't self-repair in seconds, like an auth failure). The only time a message ever really gets dropped is a long retention backstop three days out, and that drop writes a critical-level log line with the request ID and the message age.

Two bugs turned up before I shipped.

The first was in the transient-error classifier. I'd broadened it to include OSError so it would catch DNS lookup failures and "network is unreachable" cases that aren't SMTP errors per se. What I didn't know was that smtplib.SMTPException is itself a subclass of OSError, so my change had swallowed every SMTP error and was treating an auth failure as transient. The failing test spelled it out: is_transient(SMTPRecipientsRefused) is False was coming back True. The fix was ordering: check the SMTP cases first and fall through to OSError only for non-SMTP network errors.

The second I caught reading the code cold, later that night. The re-drive sweep pulled a message off the shelf with LPOP, sent it, and if that failed pushed it back. There's a gap between the pop and the push-back where a crash would lose the message entirely, and the whole premise of "never lose a message" collapses in that gap. The fix is a well-known reliable pattern: use LMOVE to atomically shift the entry to a "processing" list, act on it, then remove it. Any orphans left on the processing list by a crashed sweep get recovered at the start of the next sweep. The pattern errs toward a rare duplicate rather than a loss.

Three walls between the form and Gmail

The deploy itself went in stages. Bring up the shared docker network on the droplet. Clone the API repo and drop in the environment file with the secrets. docker compose up -d --build. Wall 1: the mail server tried to deliver to itself. Postfix bounced the first send with mail for keepbreath.ing loops back to myself. The cause was one line in /etc/hosts: 127.0.1.1 keepbreath.ing keepbreath. When Postfix asked DNS where to deliver mail for keepbreath.ing, that hosts file entry answered first, before Postfix ever hit an MX lookup. So Postfix delivered to its own IP, saw the domain wasn't in its list of local domains, and bounced.

The fix was one word: change keepbreath.ing in that hosts line to mail.keepbreath.ing. The box's real identity is mail.keepbreath.ing, and the apex belongs in DNS pointing at Cloudflare, not on a local /etc/hosts line.

Wall 2: DigitalOcean blocks outbound SMTP. With the loopback bug fixed, Postfix did a proper MX lookup, signed the message with DKIM, and then couldn't reach Cloudflare's mail servers at all. Connection timed out on port 25. Network unreachable on IPv6. I ran a direct test from the box: nc to ports 25, 465, and 587 timed out against any server I tried, while general outbound on 443 worked fine and the box's own firewall was inactive.

DigitalOcean blocks outbound SMTP on droplets. Their documentation confirms it and explicitly discourages self-hosting mail from their platform. Port 2525 is the one they leave open, because it's the standard fallback that transactional relays like Postmark, SendGrid, and Brevo listen on.

This one shot a hole in a decision I'd made earlier in the build, when I chose to self-host Postfix rather than relay through a transactional email service. I'd based that choice partly on "port 25 is open." That's half true. Inbound 25 is open on my droplet, so the box can receive mail fine. Outbound 25 is blocked, so the box can't send direct-to-MX. The contact form needs the outbound direction, which is the side my assumption got wrong. The right check would have been one nc -zv smtp.gmail.com 25 command from the droplet, three weeks earlier, before I committed to the self-hosted design.

So I needed a relay on port 2525 to send outbound at all. I picked Brevo because it has a permanent free tier of about 300 messages a day, supports port 2525, and lets me keep my own DKIM signing so authentication still lines up.

Wall 3: Brevo accepted the message but would not deliver it. With Postfix pointed at Brevo, the next send appeared to work. Postfix got a 250 OK response from Brevo, and there were no obvious errors on the server. But the message never showed up in Gmail, not in the inbox, spam, or trash.

That sent me into Brevo's dashboard and documentation. I worked through the sending logs in the web interface until I found the real status: Brevo had accepted the message into its queue, then stopped it because keepbreath.ing had not been authenticated as a sending domain in my account.

The 250 OK only meant Brevo had accepted responsibility for the message from Postfix. It did not mean Brevo had completed delivery to Gmail. Before Brevo would send mail for my domain, I had to prove that I controlled it by publishing the DNS records it provided. Until then, the message could look successful from my server while never leaving Brevo's side.

The fix was three DNS records: two DKIM CNAMEs at brevo1._domainkey and brevo2._domainkey, and a verification TXT record at the domain root. Brevo also suggested adding its own DMARC record, and I skipped that one on purpose. A domain can only have one DMARC record; adding a second wouldn't override the first, it would just break DMARC for the whole domain. I checked the existing DNS before touching anything, which is what caught it.

The one-word bug

I finished the deploy, went to bed, and took a couple of days away from the project to focus on schoolwork. The honest answer was no. I had tested the API directly by solving ALTCHA challenges in Python and posting the payload with curl. That proved the backend path could accept a valid submission. It did not prove that the browser widget could fetch a challenge, solve it, and hand a token to the form.

So I opened the page, filled it out, and clicked Send. Nothing happened. The button never changed to "sending…," no success message appeared, and no error appeared either. The form just sat there.

My first stop was the browser's developer tools. The Console had two warnings I already knew about: an inline style blocked by CSP and Cloudflare's injected analytics beacon. Neither explained why the form was inert. Then I checked the Network tab. There was no request to /api/contact at all.

That narrowed the problem down quickly. The Flask endpoint, Redis queue, worker, Postfix configuration, Brevo relay, and Gmail delivery path could not be the reason the form was failing, because the browser had never tried to submit anything. The failure had to be earlier in the page: either the form JavaScript or the ALTCHA widget.

I turned on the widget's debug output and looked more closely at its browser error. ALTCHA was trying to fetch a challenge, but it was receiving HTML instead of the JSON it expected:

ALTCHA [name=altcha] verification failed
Error: Server responded with invalid content-type.
Expected application/json, received text/html.

That error gave me something concrete to check. I compared the deployed <altcha-widget> markup with the ALTCHA integration documentation for the version I had pinned. The version I was using expected the challenge endpoint in the challenge attribute. My page still used challengeurl, an attribute from a different integration pattern or version. The widget did not read challengeurl, so it fell back to an empty endpoint.

My HTML had this:

<altcha-widget challengeurl="/api/challenge">

It needed to be this:

<altcha-widget challenge="/api/challenge">

Because challengeurl was ignored, the widget had no usable endpoint. The browser resolved the empty request against the current page, fetched contact.html, and got text/html back instead of challenge JSON. ALTCHA refused the response, never generated a proof-of-work token, and the form had nothing valid to submit. That is why the page looked fine while the button did nothing.

The fix was one word in one file.

The bug shipped because I had tested the wrong boundary. My Python and curl tests proved that the server could create and verify ALTCHA challenges. They did not include the browser widget, which was the one part responsible for fetching that challenge and attaching the completed token to a real form submission. My notes even said, "syntax-checked, but untested until deployed." I knew the browser test was missing, wrote it down, and still moved on without doing it.

Before deploying the fix, I used Playwright to test the exact one-line change against the live page. I intercepted the page response, changed only challengeurl to challenge in memory, and left every other request going to production. Playwright can monitor and modify a page's HTTP traffic, which made it useful for testing that single correction without changing the live file first.

With that one change in place, the challenge endpoint returned 200 in 34 milliseconds, the browser solved the proof-of-work in about a second, /api/contact returned 202 Accepted, the success message appeared, and the email arrived in Gmail.

The address and the mail server

The public-facing address is contact@keepbreath.ing. The mail server behind it lives at mail.keepbreath.ing, on its own A record with its own reverse DNS. Keeping the mail infrastructure on a subdomain keeps its reputation scoped to that subdomain instead of spilling onto the apex.

The address itself is really a set of DNS records. As long as those records stay valid, whatever server is answering underneath is replaceable. I renamed the droplet halfway through this build (more on that in Step 3), and the address kept working straight through the change because the address was in DNS and not on the box.

Step 2: sending my own mail with Postfix

I chose Postfix. It's well-documented and most tutorials use it, which made it a sensible default for what I was doing. Postfix on this box does two related jobs. It runs a submission service on port 587 that Gmail authenticates to and hands outgoing mail to, and it runs a relay on port 25 that delivers those messages onward to the recipient's mail server. It's the same daemon running as two services.

Postfix identity

There were three settings I had to change from the installer defaults.

The first was myhostname = mail.keepbreath.ing, which is what Postfix announces when it greets another server. It has to match the mail DNS record, the certificate's Common Name, and the reverse DNS. The Debian installer had set it to the bare keepbreath.ing, which would have failed every one of those matches, so I corrected it.

The second was mydestination = $myhostname, localhost, which is the list of domains this server considers local. I deliberately kept the parent domain off the list. Cloudflare is the MX for keepbreath.ing, so if this box also claimed the domain it would try to keep mail for @keepbreath.ing locally, and that would break the inbound routing from Step 1. The installer default included both the parent domain and a localhost.ing artifact from the .ing TLD, both of which I removed. The .ing artifact caught me by surprise the first time I read the config. Most defaults assume a .com domain, and there are a few places in the mail stack where a short TLD makes the automatic naming behave oddly.

The third was mynetworks = 127.0.0.0/8 [::1]/128, which sets loopback as the only network trusted to relay without authenticating. Only processes running on the box itself get that trust. Gmail isn't on the box, so Gmail has to log in like any other remote client. That's half of the defense against becoming an open relay for the internet.

TLS

No password is going over the wire in cleartext, so TLS has to work before I can turn on authentication.

I pointed Postfix at a Let's Encrypt certificate for mail.keepbreath.ing, obtained via DNS-01 through Cloudflare because I didn't want to expose an HTTP challenge endpoint on the box. The certificate's Common Name is mail.keepbreath.ing, which matches myhostname. A Cloudflare Origin Certificate wouldn't work in this position because only Cloudflare trusts those, and a self-signed certificate would be refused by mail clients.

For port 25 I set smtpd_tls_security_level = may, which is opportunistic encryption. It uses TLS if the sender's server supports it and accepts plaintext otherwise. That's the right posture on port 25, because you can't force every mail server on the internet to have TLS. Port 587 requires TLS, and that setting comes a few paragraphs down.

SASL through Dovecot

Postfix doesn't check submission passwords itself. It hands the check to a SASL provider. I used Dovecot as that provider, with no mailboxes and no IMAP running. The inbox lives in Gmail via the Cloudflare routing from Step 1.

The submission credential for contact@keepbreath.ing sits in /etc/dovecot/passwd as a SHA512-CRYPT hash. The plaintext is only in my offline password manager, because I need it once more in Step 4. Reading the file on the server exposes nothing usable to an attacker.

I disabled Dovecot's default PAM passdb explicitly, because a mail submission credential shouldn't double as a way to log into a Linux account.

Postfix and Dovecot talk to each other over a Unix socket that Dovecot places inside Postfix's chroot at /var/spool/postfix/private/auth. Two Postfix directives point at that socket:

smtpd_sasl_type = dovecot
smtpd_sasl_path = private/auth

I confirmed the credential worked before exposing anything to the network:

$ doveadm auth test contact@keepbreath.ing
auth succeeded

Seeing that auth succeeded line was the first real sign the plumbing was actually connected. Everything before it had been configuration on faith.

The submission service on port 587

Port 25 accepts inbound mail from other servers. Port 587 is a separate service for authenticated outbound clients. Postfix runs both from the same daemon using per-port overrides in master.cf.

The 587 block overrides five settings from the defaults. It requires TLS, enables SMTP AUTH, adds the two open-relay guards, and gives the service its own log label so I can grep for it:

submission inet n       -       y       -       -       smtpd
  -o syslog_name=postfix/submission
  -o smtpd_tls_security_level=encrypt
  -o smtpd_sasl_auth_enable=yes
  -o smtpd_relay_restrictions=permit_sasl_authenticated,reject
  -o smtpd_client_restrictions=permit_sasl_authenticated,reject

The permit_sasl_authenticated, reject value on both restriction lines is what actually keeps the service from being an open relay. Any client that has authenticated is allowed to relay through the service, and anything else is refused. There's deliberately no permit_mynetworks on this service, because port 587 is meant for remote authenticated clients rather than local processes, and letting a local process relay through it would open a hole.

Before opening the firewall I ran an open-relay test with swaks. I connected to Postfix on the loopback, skipped authentication, and asked it to relay to an outside address. It refused:

554 5.7.1 <localhost[127.0.0.1]>: Client host rejected: Access denied

That refusal was the one I actually wanted to see. It's the whole point of the restriction lines above, and it landed exactly the way the config said it should.

The same test showed two other things I wanted to check. AUTH was only advertised in the EHLO reply after STARTTLS (the pre-STARTTLS EHLO didn't include AUTH at all), so a password can never be offered before the connection is encrypted. And the certificate presented was the real Let's Encrypt one, served over TLS 1.3.

Opening 587 in the firewall

Once the open-relay test passed, I added one inbound rule to the DigitalOcean Cloud Firewall for tcp/587 from 0.0.0.0/0 and ::/0. I added it via the DigitalOcean API using curl from my laptop. My DO API token lives in the laptop's password manager and has never been on the droplet. That token can create and destroy anything in the account, so there's no reason for it to sit on a server.

I considered restricting 587 to Google's IP ranges instead of leaving it open. Gmail's send-as relay uses a broad and shifting set of Google addresses, and keeping an allowlist current would be a maintenance chore. So I left the port open to everyone, and the port's protection is TLS, SASL authentication, and the open-relay guards. The consequence of leaving it open is that internet bots will try to brute-force the login. A long random password makes guessing it impractical, but I'm not going to pretend a compromised credential is harmless: an authenticated client is allowed to relay, so a stolen or guessed password would be a real spam channel. That's exactly why the password is long and random, and why fail2ban to auto-ban repeated attempts and log monitoring are on my follow-up list.

I verified the port was reachable from an outside machine:

$ nc mail.keepbreath.ing 587
220 mail.keepbreath.ing ESMTP Postfix

Step 3: publishing SPF, DKIM, and DMARC

The next thing I set up was the DNS records that mail receivers use to decide whether to trust mail from my domain. If those records aren't right, no amount of well-configured Postfix helps. There are three of them, plus a reverse DNS record on the droplet's IP.

SPF

SPF is a DNS TXT record that names which servers are authorized to send mail for your domain. Cloudflare Email Routing had already published one for me:

v=spf1 include:_spf.mx.cloudflare.net ~all

That authorized Cloudflare's servers and nothing else. My droplet, now also a sender, wasn't on the list. A receiver checking SPF on mail from my IP would see the IP wasn't authorized to send as keepbreath.ing.

A domain has exactly one SPF record. Adding a second one breaks SPF entirely for the domain, so instead of publishing a new record I edited the existing one through Cloudflare's API:

v=spf1 ip4:YOUR.DROPLET.IP include:_spf.mx.cloudflare.net ~all

I kept ~all (softfail) rather than moving to -all (hardfail) for now. Softfail tells receivers to treat unauthorized senders as suspicious, and hardfail tells them to reject outright. I want to watch my own mail behave cleanly for a while before asking receivers to hardfail on anything.

DKIM

SPF checks the sending IP. DKIM goes further. It attaches a cryptographic signature to every outgoing message using a private key on the sending server, and it publishes the matching public key in DNS. Receivers use the public key to verify that a message really came from the domain and hasn't been altered in transit. Unlike SPF, DKIM signatures also survive forwarding.

I installed OpenDKIM as the signing daemon, generated a 2048-bit RSA key pair, and published the public key at mail._domainkey.keepbreath.ing. For the OpenDKIM configuration and its integration with Postfix I mostly worked from LinuxBabe's mail server tutorials, which walk through the signing setup and the follow-on OpenDMARC piece step by step. My selector is mail. Cloudflare's existing DKIM record uses a different selector (cf2024-1), so both records live in DNS without conflicting.

Two OpenDKIM defaults were wrong on this system, and I caught them from reading through the config carefully before touching anything else. The default socket is a Unix socket at /run/opendkim/opendkim.sock, which chrooted Postfix cannot reach. I changed it to inet:8891@localhost so Postfix could talk to it regardless of chroot, and this was the same problem I'd already run into with Dovecot. The second one is that /etc/default/opendkim is a legacy file that systemd ignores on modern distributions, which means all settings have to be in /etc/opendkim.conf instead. Catching both of these before starting the service saved me the debugging time I would otherwise have spent on them.

Then I wired OpenDKIM into Postfix as a milter, which is Postfix's plugin interface for filters that inspect or modify mail as it passes through:

smtpd_milters = inet:localhost:8891
non_smtpd_milters = inet:localhost:8891
milter_default_action = accept

The milter_default_action = accept line is deliberate. If OpenDKIM ever falls over, Postfix will pass mail through unsigned rather than dropping it. For a personal contact address I'd rather have quiet degradation than an outage.

I verified the DNS record against the private key with opendkim-testkey, which returned key OK. There's also a key not secure message that comes alongside, which is just the tool telling me I haven't set up DNSSEC on the domain, and DNSSEC isn't in scope for this build.

DMARC

DMARC sits on top of SPF and DKIM. It does two things at once. It tells receivers what to do with mail from your domain that fails both checks, and it asks receivers to send back reports about who is sending mail as your domain.

I published a minimal DMARC record at _dmarc.keepbreath.ing:

v=DMARC1; p=none; rua=mailto:contact@keepbreath.ing

p=none is monitor mode. It doesn't ask receivers to do anything to failing mail; it just asks them to send reports. I want to see the reports and confirm my own mail is passing both checks before tightening the policy to quarantine or reject. The reports come back to contact@, which the inbound routing from Step 1 forwards into Gmail.

The reverse DNS problem

I ran a test message through mail-tester, which grades outgoing mail against the standard authentication checks. It came back at 8.9 out of 10. The only real ding was RDNS_NONE.

Reverse DNS is a lookup that takes an IP address and returns a hostname. A receiver getting mail from my droplet's IP can ask DNS "what's the name of that IP?" and expect a well-configured mail server to answer with a name that matches its myhostname and forward-resolves back to the IP. A mail server whose reverse lookup goes nowhere, or points to a name that doesn't forward-resolve back, doesn't look trustworthy from the receiver's side.

Meanwhile in Gmail's Show Original view for the same message, SPF, DKIM, and DMARC all showed PASS, and the message had still gone to my Gmail spam folder. The rig gave me a near-perfect score and Gmail put the message in spam anyway. I couldn't find that gap explained in any of the tutorials I read, and I spent a while wracking my brain trying to find a path through it. Most of the useful information I ended up finding came from DigitalOcean's own DNS documentation and from digging through community forum threads where other people had hit the same issue.

The reason for the RDNS_NONE ding is a DigitalOcean-specific quirk in how droplet naming maps to PTR records. On DigitalOcean there's no separate PTR field for a droplet. The PTR record for a droplet's IP is derived from the droplet's name, and that name has to be a fully-qualified domain name that forward-resolves back to the droplet's IP.

My droplet was named keepbreath.ing, so DigitalOcean had set its PTR to keepbreath.ing. But keepbreath.ing is Cloudflare-proxied, which means any DNS lookup for that name returns a Cloudflare address rather than my droplet's IP. A receiver running the check "does this IP's reverse-DNS name forward-resolve back to this IP?" got a mismatch every time, and that mismatch is what RDNS_NONE means.

I couldn't rename the droplet to some arbitrary domain and have the check pass, because the apex is proxied through Cloudflare. The only name that forward-resolves straight to the droplet is mail.keepbreath.ing, which I'd left unproxied. So I renamed the droplet from keepbreath.ing to mail.keepbreath.ing through the DO API. The rename updated the PTR automatically. There was no downtime and no reboot, and propagation took a few minutes.

I re-ran mail-tester, which came back with 10 out of 10 and no RDNS_NONE ding.

Renaming the droplet to mail.keepbreath.ing fixed the reverse DNS problem, but I wasn't happy leaving the whole box named after its mail role when the same droplet still hosts the site itself. That gave me an obvious next project: spin up a second droplet, migrate the site to it, and let the original box stay dedicated to the mail server and (eventually) the Flask backend. DO droplets are cheap enough that I can afford to run a second one, and the split gives me a clean separation between the public web front and the services running behind it. Really I'm treating this whole site as a long-running platform for hands-on learning across web development, hosting, and the various ways servers and clients talk to each other. The plan is to keep building it out over time, adding functionality that gives me an excuse to learn something new each time. Splitting the site off from the mail server is the first of those experiments.

Step 4: telling Gmail to use it

In Gmail's settings I went to Accounts and Import, then Send mail as, then Add another email address. I entered contact@keepbreath.ing, gave mail.keepbreath.ing:587 as the SMTP server, checked the TLS box, and pasted the SASL credential from the offline password manager. Gmail sent a verification link to contact@, which forwarded through Cloudflare into the same Gmail inbox. I clicked through it.

Now contact@keepbreath.ing is a selectable identity in Gmail's From dropdown. Anything I send from that identity goes out through my own SMTP server, gets DKIM-signed on the way, and arrives at the recipient as if it had come directly from contact@keepbreath.ing. My Gmail address isn't in any header the recipient can see.

I sent one final test from Gmail-as-contact@ to mail-tester, and it came back at 10 out of 10 on the actual path I'll be using in practice.

What Gmail did with the first messages

The very first test message I sent to my own Gmail account (before the PTR fix) went straight to spam. This wasn't a surprise. SPF, DKIM, and DMARC all passed in the Show Original view, but a brand-new sending IP from a random droplet doesn't get inbox placement, and I knew that going in. Reputation takes time to build.

What I was really watching for was the retest after the PTR fix. When I sent that one, Gmail briefly held it with a 4xx "try again later" response before accepting it a few minutes later. That's greylisting: the receiver refuses the first delivery attempt with a temporary failure code and waits to see whether the sender comes back. Postfix's default behavior is to retry deferred deliveries on a backoff schedule, so my server tried again a few minutes later and Gmail accepted it. The message landed in the inbox with all three authentication checks green in Show Original, and that was the moment I knew the finish line was in view. Everything else was going to be time and consistent sending.

The greylisting isn't a failure. It's a normal check on a first-time sender, and my server responding to it correctly is one small piece of the reputation Gmail is watching for.

I also noticed something about outbound port 25 on new DigitalOcean droplets. Community forums and many tutorials will tell you DigitalOcean blocks outbound 25 on new droplets by default. Mine wasn't blocked, but my droplet has been up for about a year and a half, and DigitalOcean lifts that restriction on accounts and droplets they've had time to observe behaving cleanly. If your droplet is new, you'll probably need to request the block be lifted or wait until your account has aged in.

This site used to be Hugo behind Caddy on a DigitalOcean droplet. Now it's hand-coded HTML behind nginx on the same droplet.

Why nginx, when Caddy was already sitting right there

Caddy is easier. It does automatic HTTPS, and I had a half-built Caddy setup on the box already. I went with nginx because it's the tool used everywhere in networking and security work, and I want to know it.

The nginx config itself was about two hours of work. The pieces around it took longer: TLS through Cloudflare, locking the origin down, and staging tests between environments.

Building it in layers

The first version was plain HTTP on port 80. Events block, http block, one server block. Inside the server block: include mime.types so browsers got the right Content-Type, and try_files $uri $uri/ =404 to fall through cleanly:

events {}

http {
    include       /etc/nginx/mime.types;
    default_type  application/octet-stream;

    server {
        listen 80;
        server_name keepbreath.ing www.keepbreath.ing;

        root  /usr/share/nginx/html;
        index index.html;

        location / {
            try_files $uri $uri/ =404;
        }
    }
}

That was the whole config at that point. No gzip, no security headers, no TLS. Gzip came next, then security headers, then TLS, then the firewall. Each layer was tested before the next went in.

That mirrors real deploy practice. Every break has an obvious cause because only one thing has changed since the last known-good state. Batch a dozen changes into a single deploy and the same break sends you back through all of them to figure out which one caused it. I was deliberately practicing that discipline here.

Locally I ran nginx under podman, not Docker. I'm on Fedora Kinoite, which is immutable, and installing Docker on an immutable OS is fighting the system for no reason. Podman runs the same OCI images and reads the same compose files. It has some Fedora-flavored quirks (SELinux wants a :z on volume mounts, and it wants the fully-qualified image name where Docker assumes docker.io), but those are one-line fixes.

Rootless podman published the port on IPv4 only, and localhost on this box resolves to IPv6 ::1 first, so curl localhost:8090 came back empty. curl 127.0.0.1:8090 worked immediately.

Security headers, and the Google Fonts trap

Once the site was serving, I added the security headers, all with the always flag so they get sent on every response including errors. The set was X-Content-Type-Options: nosniff, X-Frame-Options, Referrer-Policy, Permissions-Policy (set to disable camera, mic, and geolocation), and Content-Security-Policy.

For the CSP I built the policy from what the site loads, not a generic template. That meant reading my own source: no inline scripts, no inline styles, no inline event handlers. That let me write a strict policy with no unsafe-inline in it anywhere. Ten minutes here. On any template-generated site it would have taken much longer.

One trap in setting this up: Google Fonts loads from two different hosts. The stylesheet comes from fonts.googleapis.com and the font files come from fonts.gstatic.com. If you allow only the first, the CSS loads and the fonts silently fail. The browser gives you a CSP violation that reads like the font files are being blocked, because they are, because you told it to. You need style-src to allow googleapis and font-src to allow gstatic. The final directive:

add_header Content-Security-Policy "default-src 'self'; script-src 'self'; style-src 'self' https://fonts.googleapis.com; font-src 'self' https://fonts.gstatic.com; img-src 'self'; connect-src 'self' https://api.github.com; frame-ancestors 'self'; base-uri 'self'; form-action 'self'; object-src 'none'" always;

I left HSTS off at this stage. Forcing HTTPS from a header before the site can serve it locks the browser into a broken state. HSTS only makes sense once TLS is proven.

TLS behind Cloudflare

Cloudflare fronts this site, so the TLS story has two legs, and the second one is easy to misconfigure. The connection from the browser to Cloudflare needs a public certificate, which Cloudflare handles. The connection from Cloudflare to my origin server needs a certificate too, but it can be one that only Cloudflare trusts. That is what a Cloudflare Origin Certificate is: valid for fifteen years, trusted only by Cloudflare, useless to any other client. Cloudflare is the only thing that should be reaching my origin anyway.

I generated the origin cert from the Cloudflare dashboard, covering the apex and the wildcard. Put the cert and key in a certs directory on the droplet, chmod 600 on the key, added the certs directory to .gitignore so the private key can't be committed by accident. Kept an offline backup of both files as their own separate files. The TLS config was two server blocks. Port 80 became a bare 301 up to HTTPS. Port 443 did the actual serving with http2, TLS 1.2 and 1.3, the Cloudflare origin cert, and HSTS at a deliberately short max-age=300 for the rollout:

server {
    listen 80;
    server_name keepbreath.ing www.keepbreath.ing;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    http2 on;
    server_name keepbreath.ing www.keepbreath.ing;

    ssl_certificate     /etc/nginx/certs/origin.pem;
    ssl_certificate_key /etc/nginx/certs/origin.key;
    ssl_protocols       TLSv1.2 TLSv1.3;

    add_header Strict-Transport-Security "max-age=300; includeSubDomains" always;
}

The short window meant I could unwind quickly if something was wrong.

I keep an environment file outside the repo for a couple of values my tooling reads at startup. When I generated the origin cert, I pasted the certificate and the private key straight into that file, like CERT=<the whole PEM block>. That file gets sourced as a shell script, so the shell tried to run the pasted PEM as commands and the tooling fell over with a wall of errors. Nothing leaked, because the file lives outside the repo. The lesson is small and permanent: a sourced env file is KEY=value only. Certificates and keys go in their own files.

I staging-tested the whole TLS setup on non-live ports (8443) before touching 443, because the live Hugo site was still up on 80 and 443 and I was not touching that until the new setup was proven from outside the box.

The cutover, and locking the origin down

The cutover itself was uneventful, which is what staging is for. Stopped the Hugo container so it released ports 80 and 443, switched the nginx compose file to publish on those ports, brought nginx up. Flipped Cloudflare's SSL mode from Full to Full (strict) at the same moment, so Cloudflare now validates my origin certificate end to end instead of accepting whatever cert the origin presents. Plain Full is the trap where the origin cert is never checked, which makes it useless.

I kept the old Hugo image on the box instead of deleting it. Retiring a container while keeping its image is a cheap rollback. If the new site had misbehaved, one command would have brought Hugo back.

One hole remained. The origin was answering on 80 and 443 for anyone on the internet. Cloudflare was fronting the site, but if someone found my droplet's IP, they could hit it directly and bypass Cloudflare's WAF and DDoS protection entirely. The fix is to allow inbound 80 and 443 only from Cloudflare's own IP ranges.

I did this with a DigitalOcean Cloud Firewall, applied at the edge before traffic reaches the droplet. Not ufw on the box. Docker writes its own iptables rules that bypass ufw, so if you rely on the host firewall for container ports, you have a firewall that reads correctly and quietly does nothing. With doctl, pulled Cloudflare's published IP ranges from their API, wrote an inbound rule allowing 80 and 443 only from those ranges, left SSH open so I didn't lock myself out:

doctl compute firewall create --name keepbreath-cf-only \
  --inbound-rules "protocol:tcp,ports:80,address:173.245.48.0/20,address:103.21.244.0/22,..." \
  --inbound-rules "protocol:tcp,ports:443,address:173.245.48.0/20,address:103.21.244.0/22,..." \
  --inbound-rules "protocol:tcp,ports:22,address:0.0.0.0/0,address:::/0"

Then I tested from three angles. The site loaded through Cloudflare. SSH still worked. A direct HTTP request to the origin IP failed with HTTP 000 instead of serving the site. A firewall you don't test from the outside is a guess.

Raising HSTS, and a Docker inode gotcha

With HTTPS proven stable, I raised HSTS from the 300-second rollout value to a full year. Edited nginx.conf, pushed the change, pulled on the droplet, ran nginx -s reload. Ran curl -I against the site to confirm.

max-age was still 300.

Ran reload again. Still 300. Checked the config file inside the container. Definitely the new value. Reload was completing without errors. The header was old.

The cause is a subtle Docker behavior. I had bind-mounted the nginx.conf as a single file. When you mount a file into a container, Docker resolves that mount to the file's inode at container start. git pull does not edit files in place. It replaces them with new files, which means a new inode. The container was still pointed at the original inode. That file no longer had a directory entry, but it still existed because the container had it open. nginx reloaded honestly. It just reloaded the config it could see, which was the stale one.

Reload alone didn't take. docker restart did:

git pull
nginx -s reload
curl -sI https://keepbreath.ing | grep -i strict
# strict-transport-security: max-age=300; includeSubDomains   <- still stale!

docker restart keepbreath
curl -sI https://keepbreath.ing | grep -i strict
# strict-transport-security: max-age=31536000; includeSubDomains

The real fix is to bind-mount the config directory instead of the single file, so an inode swap on the file inside no longer matters. That's on the backlog now.

What I learned

Curl looked broken because localhost resolved to IPv6 while podman had only bound the port on IPv4. A pasted certificate became a shell command because I put it in a file that got sourced. A squash-merge left git branch -d complaining a branch wasn't merged. Docker served a stale config because the bind mount was pinned to an inode git pull had orphaned. Docker's iptables writes bypass ufw entirely, which is why the firewall had to live at the DO edge.

The current box is running end-of-life Ubuntu and needs to be replaced. There's a saying you'll hear in DevOps circles: "cattle, not pets." The phrase was coined around 2011 by Bill Baker at Microsoft and popularized by Randy Bias of CloudScaling. Pets are servers you name, feed, and nurse back to health when they break. Cattle are numbered, interchangeable, and replaced when they fail. The point of keeping your infrastructure in code is to move a server from the first category to the second.

Because my whole stack now lives in git, this box is cattle. The next post is standing up an identical stack on a fresh LTS droplet and cutting DNS over to it.

I made Pong in Python. It's the game everybody makes first, which is why I picked it. I wanted practical experience on something small enough to actually finish, so I started it on my own outside of class.

The plan going in was to keep iterating on it until it was polished. This post covers the first stretch of that, from a working Pong to one that's worth playing.

The basic version worked and it was boring. Nothing broken about it. Ball moved, paddles moved, score counted, somebody won. The problem was that there was nothing to do. The ball hit a paddle and reversed, which meant both players could stand still, tap a key when it got close, and rally like that until they got tired of it.

The physics

I made the contact point on the paddle set the return angle and the return speed.

offset = (ball.y - paddle_center) / (paddle.height / 2)

speed_y = offset * 6 + paddle.dy * 0.4
speed   = 4 + abs(offset) * 5 + abs(paddle.dy) * 0.7
speed   = min(speed, 16)
speed_x = direction * speed

So offset runs from about -1 at the top of the paddle to +1 at the bottom, with 0 dead center. Take the ball in the middle and it comes back slow and flat. Take it out near the tip and it comes back fast and steep.

So now you're aiming with the paddle. The middle is the safe place to meet the ball and it keeps the rally alive. The tip is where the dangerous shots come from, and it's also the part of the paddle you can miss with.

The paddle.dy in both lines is the paddle's own motion at the moment of contact. If you're sweeping when you connect you add pace regardless of which way you're moving, and you add angle in the direction of the sweep. Brush upward and the ball leaves upward.

A corner hit while sweeping hard is the whole game. That's how you score. Against the computer it's close to the only way you score, because anything softer gets read and sent back at you.

Which is why the speed is capped at 16. The ceiling isn't there to protect the computer, it's there to protect you. Uncapped, that same shot works just as well coming the other direction, and on HARD you end up facing balls that no human hand is getting to. The window is narrow. Fast enough that a rally has some threat in it, slow enough that a player who reads the shot can still get there.

Then the ball got stuck in the paddle

This one needs some setup, because the bug doesn't make sense until you know how the game actually moves.

The ball doesn't slide across the screen. Sixty times a second the program wakes up, adds the ball's speed to its position, checks what it's touching, and draws the result. The ball is teleporting. It's just teleporting in steps small enough that your eye reads it as motion.

My collision check was one idea. If the ball's box and the paddle's box are overlapping, flip the horizontal speed and send it back the other way.

At four pixels a frame that holds up fine. The ball only ever dips a few pixels into the paddle before it gets turned around, and by the next frame it's clear.

At sixteen it falls apart. The ball can land most of the way inside the paddle in a single jump. The code sees the overlap and flips it. Next frame the ball has only backed out sixteen pixels, and if it landed deeper than that, it's still inside the paddle. So the code sees an overlap again and flips it a second time, back into the paddle. Then out. Then in.

The ball sat there and vibrated. I let it run for a good while because I wasn't sure what I was looking at.

So I made two changes. The ball only gets turned around if it's actually heading into the paddle, which leaves one that's already on its way out alone. And the moment it makes contact, I move it so it's sitting flush against the face of the paddle, which clears the overlap before the next frame ever looks at it.

Then it went straight through the paddle

Same root problem wearing a different hat.

I was working out which direction to bounce by comparing the paddle's position to the ball's. If the paddle was to the left of the ball, send the ball right, and so on. Reasonable, until the ball jumps deep enough in one frame that its center ends up on the far side of the paddle's center. Now the comparison says the paddle is on the right, so the code sends the ball right, straight on through and out the back for a point. It did exactly what I told it to do.

I fixed it by not asking. The left paddle is on the left half of the screen and it is never going to be anywhere else, so I read the side off the screen half instead of recalculating it from two things that are both moving.

Corners were a smaller version of the same thing. Fast diagonals kept sneaking past the paddle tips through a very short overlap window, so I ran the collision box six pixels past each end. The paddle still draws at its real size and the angle math still uses the real height. The tips are just a little more generous than they look. I'd rather have that than a game that's technically correct about six pixels while your best shot of the night goes through the wall.

The computer got very good at being bad

I didn't see this one coming at all.

My CPU worked the way you'd expect. Follow the ball, center the paddle on it, hit it back. Under the old physics that made a decent opponent. Under the new physics it made the worst opponent that can exist, because centering the paddle produces the slowest, flattest shot in the game.

I had built something that accidentally optimized for playing badly. Every rally turned into the computer lobbing soft floaters at me until I lost interest.

So I gave it a plan instead of a position. When you return the ball, the CPU looks at where your paddle is sitting and picks a spot on its own paddle that will send the ball to the opposite half of the court from you. You're up high, it strikes low. It's trying to make you run.

It picks a new target every single time you hit the ball. That's what makes it feel alive. A long rally becomes a string of different attacks instead of the same one on a loop, and when the ball is heading away from it, it stops shadowing you and drifts back toward center.

Forty lines or so. Completely different game after that.

Difficulty

DIFFICULTY = {"EASY": (5, 18), "NORMAL": (7, 30), "HARD": (9, 42)}

Each level is two values. The first is how fast the computer's paddle can move, and the second is how far toward the corner it aims when it swings.

EASY moves slower than you do and aims politely, so you can beat it by putting the ball where it isn't. HARD matches your paddle speed and goes for the edges. None of it touches the ball itself. What changes between the levels is how good the opponent is at playing.

I still can't beat it on HARD. I can score on it, which is how I know the level is winnable and not just a wall, but taking one all the way to fifteen would mean practice hours I don't have right now. That doesn't bother me. I'd rather the top setting be something I have to grow into than something I cleared the first night I built it.

The dumbest bug in the project

The win screen could be dismissed by any key at all. So if you happened to be holding a movement key at the moment the last point landed, which is exactly what you're doing during a final rally, it appeared and vanished inside the same frame.

The reason it took me so long to catch is that I almost never got there. Most of my testing stopped well short of fifteen points, because I'd notice something off, change it, and start over. And once the physics were tuned but before I'd added difficulty levels, I couldn't beat the computer at all.

The first game I ever played through to a win was on EASY, after the difficulty settings went in. I scored the fifteenth point, something flickered, and I was back at the menu. Locking dismissal to Enter and Space fixed it, and the second time I won I actually got to look at it.

Where it stands

One player or two, difficulty levels, an opponent that plays you, scoring, a win screen, a rematch. By any reasonable definition that's a finished game. It's just a plain one.

There are no image files and no sound files anywhere in this. Every single thing on the screen is a rectangle, a circle, or rendered text. I built it that way because I wanted it to be fun as plain shapes before I spent one minute making it look like anything. A game that plays well and looks plain is still worth playing.

So the next pass is making it look like something, and then seeing how much more game I can hang off a loop that already works:

  1. Space age pinball. Real palette, glow on the paddles and the ball, a tracer behind it, flashes when somebody scores.
  2. Bumpers out in the field to kick the ball around and pay out points.
  3. Multiball, or a different mode entirely, once the rest of it is finished.

That's the whole reason I started with Pong. It's small enough to finish and open enough to keep going.
